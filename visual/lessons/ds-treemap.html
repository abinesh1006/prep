TreeMap and TreeSet: a red-black tree

A TreeMap keeps its keys sorted in a binary search tree that repairs itself after every insert and delete, so it never gets taller than about 2 log₂ n. That buys you O(log n) get and put, plus questions a HashMap cannot answer: "what is the largest key ≤ x?", "all keys between a and b", "the smallest key".

Time to learn: about 2 hours · Prerequisites: Binary search trees, HashMap

Use it when you need…
  • sorted keys while inserting and deleting: firstKey, lastKey, in-order iteration;
  • nearest key queries: floorKey(x) (largest ≤ x), ceilingKey(x) (smallest ≥ x), lowerKey, higherKey, all O(log n);
  • ranges: headMap(x), tailMap(x), subMap(a, b);
  • a sorted multiset or a priority queue with fast removal of any element (TreeMap<value, count>).

In plain words

A binary search tree keeps every smaller key to the left and every bigger key to the right, so a search goes down one path. The catch: if you insert 1, 2, 3, 4, … in order, every new key goes to the right of the last one and the "tree" is a straight line. Search becomes O(n).

A red-black tree is a binary search tree with one extra bit per node, a colour, and four rules:

  1. Every node is red or black.
  2. The root is black.
  3. A red node never has a red child (no two reds in a row).
  4. Every path from a node down to an empty spot (null) passes through the same number of black nodes.

Why this keeps it short: by rule 4 every path has the same number of blacks, say b. By rule 3 reds can only sit between blacks, so no path is longer than 2b. The shortest path is at least b, so the longest path is at most twice the shortest. That is enough to prove height ≤ 2 log₂(n + 1): with a million keys, at most about 40 levels.

After an insert, a rule may break. The tree fixes it locally with two tools: recolouring (flip colours) and rotations (re-hang three nodes so a different one is on top, keeping the left-to-right order). At most two rotations per insert.

Analogy

A library shelf system where every corridor from the entrance to a dead end must pass the same number of "black" signposts, and two "red" signposts may never stand next to each other. When you add a book and a rule breaks, a librarian either repaints a few signposts or swings one small section of the shelving around a pivot. The books stay in alphabetical order the whole time; only the corridors get shorter.

What it looks like in memory

Each node is a TreeMap.Entry object: key, value, left, right, parent and a boolean colour. Below, keys 50, 30, 70, 20, 40, 60, 80, 35, 45 inserted in that order. Dark filled nodes are black, red outlined nodes are red.

One node costs about 40 bytes plus your key and value objects: key, value, three child/parent references and the colour flag. A HashMap node is similar in size, but a TreeMap needs no table array.

Watch the operations

1. Insert in sorted order: one rotation saves the day

Put 10, 20, 30. A plain BST would become a line 10 → 20 → 30. The red-black tree sees "two reds in a row on a straight line" and rotates.

2. Red uncle: just recolour, and push the problem up

Continue with put 5. Its parent 10 is red, and so is its uncle 30. No rotation: flip three colours. The grandparent becomes red, which here is the root, so it is painted back to black.

3. Triangle: two rotations

Now put 7. It goes right of 5, which is left of 10: a zig-zag ("triangle"). One rotation turns it into a line, a second rotation lifts the middle key, 7, to the top of that little subtree.

4. The payoff: ten sorted inserts

The worst input for a plain BST is sorted input. Put 1, 2, …, 10 and watch the height stay near log₂ n while a plain BST would be 10 levels tall.

5. floorKey, ceilingKey and headMap: walk one path, remember the best

On the tree from the memory section, ask floorKey(42) (largest key ≤ 42) and ceilingKey(42) (smallest key ≥ 42). Each step goes left or right exactly like a search, and remembers the best candidate seen so far.

Build it yourself

Interviewers rarely ask for a full red-black tree, but they do ask "how does TreeMap stay balanced?" and sometimes "write insert with rotations". This is the textbook (CLRS) insert, the same algorithm as TreeMap.fixAfterInsertion, plus get, floorKey and ceilingKey. Delete is left out (it has six cases; nobody writes it in 45 minutes). Tested against java.util.TreeMap: 200 random and sorted runs up to 2,000 keys, checking every rule, the height bound and every floor/ceiling answer.

The direction trick: rotate(x, true) is a left rotation (the right child moves up), rotate(x, false) a right rotation. The mirror cases (parent is a right child) then share the same code by passing pLeft or !pLeft.

The real Java class

  • Algorithm: TreeMap is a red-black tree "adapted from Cormen, Leiserson and Rivest" (its Javadoc). put does a BST walk, links a new Entry, then fixAfterInsertion: the same three cases as above. remove uses deleteEntry + fixAfterDeletion (at most three rotations).
  • Entry: key, value, left, right, parent, boolean color. In the JDK source RED = false and BLACK = true. The parent link lets iterators find the next key (successor) without a stack.
  • Ordering: the Comparator you pass, or the keys' compareTo (natural order). It never calls hashCode or equals: two keys are "the same" when compare returns 0.
  • Nulls: with natural ordering a null key throws NullPointerException. Null values are fine.
  • Navigation (NavigableMap): firstKey/lastKey, floorKey/ceilingKey (≤ / ≥), lowerKey/higherKey (< / >), the …Entry versions, pollFirstEntry/pollLastEntry (remove and return min / max), descendingMap(). Since Java 21 TreeMap is also a SequencedMap (firstEntry, reversed(); putFirst throws because the order is decided by the keys).
  • Range views: headMap(to) excludes to, tailMap(from) includes from, subMap(from, to) is [from, to). Overloads with booleans choose inclusive or exclusive. Views are live: changes show through both ways, and putting a key outside the view's range throws.
  • TreeSet is a thin wrapper around a TreeMap<E, Object>; every element is a key mapped to one shared dummy value PRESENT. Same costs, methods first, last, floor, ceiling, lower, higher, pollFirst, headSet, tailSet, subSet.
  • Not thread-safe. The concurrent sorted map is ConcurrentSkipListMap (a skip list, not a tree). size() is O(1) (a counter); containsValue is O(n).

Why and when to use it

TreeMap beats HashMap when the question involves order. A HashMap answers "is 42 here?" in O(1) but has no idea which key is closest to 42; you would scan all n keys. A TreeMap answers both in O(log n). Typical cases:

  • Nearest key: "the booking that starts at or before time t" (floorEntry), My Calendar, "closest value in a stream", stock price at a timestamp (Time Based Key-Value Store).
  • Sorted multiset with removal: TreeMap<Integer, Integer> of value → count: sliding window max/min/median of arbitrary elements, "contains duplicate III" (any value within t), merge of intervals as they arrive.
  • Min and max at once with deletion, which a single heap cannot do: firstKey() and lastKey().
  • Sorted output after many updates: iterate in key order without sorting.
  • Guaranteed worst case: always O(log n), no bad hash functions or resize pauses.

When not to use it

  • Only exact lookups (count, seen-before, two-sum): HashMap / HashSet, O(1) average and about 2 to 5 times faster in practice.
  • Only the minimum, repeatedly, and no arbitrary removals: PriorityQueue (O(1) peek, compact array, smaller constant).
  • Keys are known up front and never change: sort an array once and use binary search (cache friendly, no node objects).
  • Need the k-th smallest or "how many keys < x" fast: TreeMap cannot do it in O(log n) (no subtree sizes). Use a Fenwick / segment tree over compressed values.
  • Keys are small integers in a known range: a plain array or a bucket array is O(1).

Used in these patterns

  • Binary search trees: the plain BST this structure balances; floor and ceiling by hand.
  • Intervals: My Calendar and merging intervals as they arrive with floorKey / ceilingKey.
  • Sliding window: a TreeMap<value, count> for window min, max or "any value within t".
  • Two heaps: sliding window median, where two TreeSets / TreeMaps allow removing the leaving element in O(log n).
  • Design problems: Time Based Key-Value Store, leaderboards, stock price tracking.
  • Greedy and Binary search: "smallest available item ≥ x" (assign tasks, hand of straights).
Remember

TreeMap = red-black BST: sorted keys, everything O(log n). Four rules (root black, no red-red, equal black count per path) keep height ≤ 2 log₂(n + 1). Insert fix: red uncle → recolour and move up; black uncle → rotate (triangle: two rotations, line: one). Reach for it when the question says closest, range, smallest/largest with deletion or sorted.

Common mistakes
  • A comparator that returns 0 for different objects: TreeMap/TreeSet treat them as the same key and silently drop one. new TreeSet<String>(Comparator.comparingInt(String::length)) keeps only one word per length. Add a tie-breaker.
  • floorKey returns Integer and can be null. int f = map.floorKey(x); throws NullPointerException when nothing is ≤ x. Store it in an Integer and check.
  • Mixing up the four: floor ≤, ceiling ≥, lower <, higher >. And headMap(x) excludes x while tailMap(x) includes it.
  • Believing firstKey() is O(1). It walks to the leftmost node: O(log n). Still fast, but not a heap's peek.
  • Using a multiset as TreeSet: duplicates vanish. Use TreeMap<value, count> and remove the key when its count hits 0.
  • Changing a key object's fields after putting it in: the tree order is now wrong and lookups fail. Keys must be effectively immutable.
  • Using (a, b) -> a - b as the comparator: same overflow trap as in PriorityQueue.

Interview questions on the internals

What data structure is behind TreeMap, and what are its rules?

A red-black tree: a BST where every node is red or black, the root is black, a red node has no red child, and every root-to-null path has the same number of black nodes.

Why do those rules bound the height?

All paths have the same black count b, and reds cannot be adjacent, so every path has between b and 2b nodes. A tree with black height b has at least 2b − 1 nodes, so b ≤ log₂(n + 1) and the height ≤ 2 log₂(n + 1).

Why is a newly inserted node coloured red?

A red node does not change any path's black count, so rule 4 stays true. Only rule 3 (no red-red) can break, and that is fixable locally by recolouring and rotations.

Walk through the insert fix-up cases.

If the parent is black, nothing to do. If the parent and the uncle are red: recolour parent and uncle black, grandparent red, and continue from the grandparent. If the uncle is black: if the node is an inner child (triangle) rotate the parent to make a line; then recolour parent black, grandparent red, and rotate the grandparent the other way. Finally paint the root black.

What does a rotation do, and does it change the sorted order?

It re-hangs a parent and child so the child goes up and the parent goes down, moving the child's inner subtree across. The in-order (sorted) sequence is unchanged; only depths change. It is O(1): a few pointer updates.

How many rotations can an insert do? A delete?

Insert: at most 2. Delete: at most 3. Recolouring can climb up to O(log n) levels, but it is just colour flips.

When would you pick TreeMap over HashMap?

When you need order: floor/ceiling (nearest key), ranges, min/max with deletion, sorted iteration, or a guaranteed O(log n) worst case. For pure lookups HashMap is faster.

How does TreeSet store elements, and how does it decide duplicates?

It wraps a TreeMap where each element is a key with a dummy value. Duplicates are decided by compare(a, b) == 0, not by equals, so the comparator must be consistent with equals or elements disappear.

Is headMap a copy?

No, it is a live view backed by the same tree, created in O(1). Iterating it costs O(log n + k). Writes through the view change the map, and keys outside its range are rejected.
