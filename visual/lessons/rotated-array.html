Rotated Sorted Array

A sorted array that was cut in two and swapped around is still easy to binary search: at every middle, one of the two halves is perfectly sorted, and that half tells you where to go.

Time to learn: about 1.5 hours · Prerequisites: Binary search

When to use it — the signal

"Sorted array rotated at an unknown pivot", "find the minimum", "search in rotated array", O(log n) required. Also: a circular sorted list, or a log file sorted by time that wraps around.

The idea in plain words

Take the sorted array [0, 1, 2, 4, 5, 6, 7], cut it after the 2 and put the front part at the back: [4, 5, 6, 7, 0, 1, 2]. That is a rotated sorted array. It is two sorted runs, 4 5 6 7 and 0 1 2, and the minimum is where the second run starts (the "drop").

  • Pick any middle. The drop is on one side of it, so the other side has no drop — it is fully sorted.
  • How to tell which side? Compare ends. If nums[lo] <= nums[mid], the left half rises smoothly, so it is sorted. Otherwise the right half is.
  • Find minimum: if nums[mid] > nums[hi], the drop (and the minimum) is to the right of mid. Otherwise mid..hi is sorted, so the minimum is mid or to its left.
  • Search for a target: look at the sorted half. Its smallest and largest values are its two ends, so you can tell instantly whether the target is inside it. If yes, go there; if no, go to the other half.
Analogy

A round clock face read starting from 4 o'clock: 4, 5, 6, … 12, then 1, 2, 3. The numbers are in order except for one jump back. Whichever half of the dial you look at, at least one half has no jump, and you can trust its order.

Why it works

"A rotation creates only one drop, so at any mid at least one half is fully sorted. A sorted half's range is just its two end values, so one comparison tells me whether the target can be there — and I discard half the array each time, O(log n)."

The template to remember

// Find min: compare with the right end
if (nums[mid] > nums[hi]) lo = mid + 1; else hi = mid;

// Search: find the sorted half, test the range
if (nums[lo] <= nums[mid]) {          // left sorted
    if (nums[lo] <= t && t < nums[mid]) hi = mid - 1; else lo = mid + 1;
} else {                               // right sorted
    if (nums[mid] < t && t <= nums[hi]) lo = mid + 1; else hi = mid - 1;
}
Remember

One half is always sorted. Find it, ask "is the target in its range?", go there or go to the other half.

Common mistakes
  • Using < instead of <= in nums[lo] <= nums[mid]: when lo == mid (two elements left), the left "half" is one element and is sorted.
  • For find-min, comparing with nums[lo] instead of nums[hi] — it breaks on an array that is not rotated at all.
  • With duplicates (LC 81, 154), nums[mid] == nums[hi] tells you nothing; shrink with hi--. Worst case becomes O(n).

Test yourself

The array is not rotated at all, [1, 2, 3, 4, 5]. Does findMin still work?

Yes. nums[mid] is never > nums[hi], so hi keeps moving left until it reaches index 0, the value 1.

How would you find how many times the array was rotated?

It is the index of the minimum — the same findMin loop, return lo.

Why can't you just search the sorted half every time?

The target may be in the unsorted half. The sorted half is only used as a quick test: "is the target in this range?" If not, it must be in the other half.
