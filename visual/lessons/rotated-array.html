Rotated Sorted Array

A sorted array that was cut in two and swapped around is still easy to binary search: at every middle, one of the two halves is perfectly sorted, and that half tells you where to go.

Time to learn: about 1.5 hours · Prerequisites: Binary search

When to use it — the signal

"Sorted array rotated at an unknown pivot", "find the minimum", "search in rotated array", O(log n) required. Also: a circular sorted list, or a log file sorted by time that wraps around.

The idea in plain words

Take the sorted array [0, 1, 2, 4, 5, 6, 7], cut it after the 2 and put the front part at the back: [4, 5, 6, 7, 0, 1, 2]. That is a rotated sorted array. It is two sorted runs, 4 5 6 7 and 0 1 2, and the minimum is where the second run starts (the "drop").

  • Pick any middle. The drop is on one side of it, so the other side has no drop — it is fully sorted.
  • How to tell which side? Compare ends. If nums[lo] <= nums[mid], the left half rises smoothly, so it is sorted. Otherwise the right half is.
  • Find minimum: if nums[mid] > nums[hi], the drop (and the minimum) is to the right of mid. Otherwise mid..hi is sorted, so the minimum is mid or to its left.
  • Search for a target: look at the sorted half. Its smallest and largest values are its two ends, so you can tell instantly whether the target is inside it. If yes, go there; if no, go to the other half.
Analogy

A round clock face read starting from 4 o'clock: 4, 5, 6, … 12, then 1, 2, 3. The numbers are in order except for one jump back. Whichever half of the dial you look at, at least one half has no jump, and you can trust its order.

Why it works

"A rotation creates only one drop, so at any mid at least one half is fully sorted. A sorted half's range is just its two end values, so one comparison tells me whether the target can be there — and I discard half the array each time, O(log n)."

The template to remember

// Find min: compare with the right end
if (nums[mid] > nums[hi]) lo = mid + 1; else hi = mid;

// Search: find the sorted half, test the range
if (nums[lo] <= nums[mid]) {          // left sorted
    if (nums[lo] <= t && t < nums[mid]) hi = mid - 1; else lo = mid + 1;
} else {                               // right sorted
    if (nums[mid] < t && t <= nums[hi]) lo = mid + 1; else hi = mid - 1;
}
Remember

One half is always sorted. Find it, ask "is the target in its range?", go there or go to the other half.

Common mistakes
  • Using < instead of <= in nums[lo] <= nums[mid]: when lo == mid (two elements left), the left "half" is one element and is sorted.
  • For find-min, comparing with nums[lo] instead of nums[hi] — it breaks on an array that is not rotated at all.
  • With duplicates (LC 81, 154), nums[mid] == nums[hi] tells you nothing; shrink with hi--. Worst case becomes O(n).

Practice in this order

  • Medium153. Find Minimum in Rotated Sorted Array — first animation.
    Show solution

    The idea

    A sorted array was rotated, like [3,4,5,1,2]: two sorted runs, and the minimum is where the second run starts. Compare the middle with the last item: if nums[mid] > nums[hi], mid is in the left (high) run and the drop is to its right; otherwise mid is in the right (low) run, so the minimum is mid or to its left. Pattern: binary search on a rotated array.

    Brute force first

    Scan for the smallest value. O(n).

    Step by step

    1. Keep lo = 0, hi = n - 1; the minimum is always in [lo, hi].
    2. While lo < hi, take mid.
    3. If nums[mid] > nums[hi], the minimum is right of mid: lo = mid + 1.
    4. Otherwise mid could be the minimum: hi = mid.
    5. When they meet, return nums[lo].

    Java

    class Solution {
    public int findMin(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            // mid in the high run: the drop is to the right
            if (nums[mid] > nums[hi]) lo = mid + 1;
            else hi = mid; // mid in the low run
        }
        return nums[lo];
    }
}

    Time O(log n) · Space O(1) — each step halves the range.

    Dry run

    nums = [4,5,6,7,0,1,2]
lo=0 hi=6 mid=3: 7 > 2 -> lo=4
lo=4 hi=6 mid=5: 1 < 2 -> hi=5
lo=4 hi=5 mid=4: 0 < 1 -> hi=4
return nums[4] = 0

    Watch out

    Compare with nums[hi], not nums[lo]: an array that is not rotated at all ([1,2,3]) breaks the nums[lo] version. A one-item array returns at once.

  • Medium33. Search in Rotated Sorted Array — second animation.
    Show solution

    The idea

    Find a target in a rotated sorted array like [4,5,6,7,0,1,2] in O(log n). Cut at mid: one of the two halves is always fully sorted. Check which one (compare nums[lo] with nums[mid]); if the target lies inside that sorted half's range, search there, otherwise search the other half.

    Brute force first

    Scan every item. O(n). Another way is to find the minimum first (problem 153) and then run normal binary search on the correct run; also O(log n), just two passes.

    Step by step

    1. lo = 0, hi = n - 1; while lo <= hi take mid.
    2. If nums[mid] is the target, return mid.
    3. If nums[lo] <= nums[mid], the left half is sorted: if nums[lo] <= target < nums[mid] go left (hi = mid - 1), else go right.
    4. Otherwise the right half is sorted: if nums[mid] < target <= nums[hi] go right (lo = mid + 1), else go left.
    5. If the range empties, return -1.

    Java

    class Solution {
    public int search(int[] nums, int target) {
        int lo = 0, hi = nums.length - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return mid;
            if (nums[lo] <= nums[mid]) {
                // left half [lo..mid] is sorted
                if (nums[lo] <= target && target < nums[mid])
                    hi = mid - 1;
                else
                    lo = mid + 1;
            } else {
                // right half [mid..hi] is sorted
                if (nums[mid] < target && target <= nums[hi])
                    lo = mid + 1;
                else
                    hi = mid - 1;
            }
        }
        return -1;
    }
}

    Time O(log n) · Space O(1) — one half is thrown away every step.

    Dry run

    nums = [4,5,6,7,0,1,2], target = 0
lo=0 hi=6 mid=3 (7): left [4..7] sorted, 0 not in it -> lo=4
lo=4 hi=6 mid=5 (1): left [0..1] sorted, 0 in it    -> hi=4
lo=4 hi=4 mid=4 (0): found -> return 4

    Watch out

    Use nums[lo] <= nums[mid] with <=: when lo == mid (two items left) the "left half" is a single item and still counts as sorted. Keep one side of each range check strict, since nums[mid] was already tested.

  • Medium81. Search in Rotated Sorted Array II — duplicates: when ends are equal, shrink by one.
    Show solution

    The idea

    Same as problem 33, but values may repeat, and we only return true or false. Duplicates break one thing: in [1,0,1,1,1], nums[lo], nums[mid] and nums[hi] are all 1, so we cannot tell which half is sorted. In that case just shrink both ends by one; they are not the target, so nothing is lost.

    Brute force first

    Scan every item. O(n), which is also the worst case of the smart version.

    Step by step

    1. lo = 0, hi = n - 1; while lo <= hi take mid.
    2. If nums[mid] == target, return true.
    3. If nums[lo] == nums[mid] == nums[hi], we cannot decide: lo++, hi--, and loop again.
    4. Else if nums[lo] <= nums[mid], the left half is sorted: go left if the target is inside it, else right.
    5. Else the right half is sorted: go right if the target is inside it, else left.
    6. Return false when the range is empty.

    Java

    class Solution {
    public boolean search(int[] nums, int target) {
        int lo = 0, hi = nums.length - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return true;
            boolean flat = nums[lo] == nums[mid]
                    && nums[mid] == nums[hi];
            if (flat) {
                lo++; // ends are not the target;
                hi--; // drop them and look again
            } else if (nums[lo] <= nums[mid]) {
                // left half is sorted
                if (nums[lo] <= target && target < nums[mid])
                    hi = mid - 1;
                else
                    lo = mid + 1;
            } else {
                // right half is sorted
                if (nums[mid] < target && target <= nums[hi])
                    lo = mid + 1;
                else
                    hi = mid - 1;
            }
        }
        return false;
    }
}

    Time O(log n) usually, O(n) worst case (all equal) · Space O(1) — the shrink step can only drop two items at a time.

    Dry run

    nums = [1,0,1,1,1], target = 0
lo=0 hi=4 mid=2: 1,1,1 all equal -> lo=1 hi=3
lo=1 hi=3 mid=2: nums[1]=0 <= 1, left [0,1] sorted,
          0 in [0,1) -> hi=1
lo=1 hi=1 mid=1: found -> true

    Watch out

    Without the "all three equal" case, nums[lo] <= nums[mid] wrongly says the left half is sorted for [1,0,1,1,1] and the 0 is missed. Say in the interview that the worst case is O(n).

  • Medium162. Find Peak Element — another "not sorted, still halvable" array.
    Show solution

    The idea

    A peak is bigger than its neighbours; the outside of the array counts as minus infinity. Like a rotated array, this one is not sorted but can still be halved: if nums[mid] < nums[mid + 1] we stand on an uphill slope, and climbing right must reach a peak. If not, mid or something on its left is a peak. Pattern: binary search on a slope.

    Brute force first

    Return the first i with nums[i] > nums[i + 1], or the last index. O(n).

    Step by step

    1. lo = 0, hi = n - 1.
    2. While lo < hi, take mid.
    3. If nums[mid] < nums[mid + 1], move right: lo = mid + 1.
    4. Otherwise keep mid: hi = mid.
    5. Return lo.

    Java

    class Solution {
    public int findPeakElement(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            // uphill: a peak is to the right
            if (nums[mid] < nums[mid + 1]) lo = mid + 1;
            else hi = mid; // downhill: mid may be it
        }
        return lo;
    }
}

    Time O(log n) · Space O(1) — half the range goes each step.

    Dry run

    nums = [1,2,3,1]
lo=0 hi=3 mid=1: 2 < 3 uphill   -> lo=2
lo=2 hi=3 mid=2: 3 > 1 downhill -> hi=2
return 2

    Watch out

    Neighbours are never equal in this problem; that is what makes the slope argument work. mid + 1 is always inside the array because mid < hi while lo < hi.

  • Hard154. Find Minimum in Rotated Sorted Array II — find-min with hi-- on ties.
    Show solution

    The idea

    Same as problem 153 but values can repeat, like [2,2,2,0,1]. Compare nums[mid] with nums[hi]: bigger means the minimum is right of mid; smaller means it is mid or left. When they are equal we cannot tell, but we can safely drop hi (hi--), because nums[mid] has the same value and stays in range.

    Brute force first

    Scan for the smallest value. O(n), which is also the worst case here.

    Step by step

    1. lo = 0, hi = n - 1; while lo < hi take mid.
    2. If nums[mid] > nums[hi]: lo = mid + 1.
    3. If nums[mid] < nums[hi]: hi = mid.
    4. If equal: hi--.
    5. Return nums[lo].

    Java

    class Solution {
    public int findMin(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] > nums[hi]) lo = mid + 1;
            else if (nums[mid] < nums[hi]) hi = mid;
            else hi--; // tie: nums[mid] keeps the same value
        }
        return nums[lo];
    }
}

    Time O(log n) usually, O(n) worst case (all equal) · Space O(1) — a tie only removes one item.

    Dry run

    nums = [2,2,2,0,1]
lo=0 hi=4 mid=2: 2 > 1 -> lo=3
lo=3 hi=4 mid=3: 0 < 1 -> hi=3
return nums[3] = 0
nums = [3,1,3]: mid=1: 1 < 3 -> hi=1; mid=0: 3 > 1 -> lo=1 -> 1

    Watch out

    On a tie, drop hi, never lo or mid: in [3,1,3] moving lo past mid could skip the 1. The question usually asks how duplicates change the time; the answer is O(n) worst case.

Test yourself

The array is not rotated at all, [1, 2, 3, 4, 5]. Does findMin still work?

Yes. nums[mid] is never > nums[hi], so hi keeps moving left until it reaches index 0, the value 1.

How would you find how many times the array was rotated?

It is the index of the minimum — the same findMin loop, return lo.

Why can't you just search the sorted half every time?

The target may be in the unsorted half. The sorted half is only used as a quick test: "is the target in this range?" If not, it must be in the other half.
