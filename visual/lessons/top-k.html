Top K Elements

To keep the k biggest things, hold them in a min-heap of size k: the weakest winner sits on top, ready to be kicked out by anyone better.

Time to learn: about 1–2 hours · Prerequisites: Heaps, Arrays and hashing

When to use it — the signal

"k largest", "kth largest", "k smallest", "k most frequent", "k closest points", "top k words". A number k much smaller than n is the giveaway.

The idea in plain words

You want the 3 largest of [3, 2, 1, 5, 6, 4, 8]. Sorting everything costs O(n log n) and does far more work than needed.

Instead keep a small "winners" group of at most k = 3 numbers, stored in a min-heap. The top of a min-heap is its smallest member — the weakest winner.

  • Each new number joins the group.
  • If the group now has 4 members, kick out the weakest (poll the min).
  • At the end, the group holds the 3 largest, and its top is the 3rd largest.

The heap never grows past k, so each step costs O(log k). Total O(n log k) — with n = 1,000,000 and k = 10 that is far cheaper than sorting.

It feels backwards: largest → min-heap, smallest → max-heap. The heap's top must be the one you would throw out.

For most frequent, first count with a hash map, then pick the top k counts — either with the same size-k heap, or with buckets: an array where bucket[f] lists the numbers seen f times. Walking buckets from the highest f down gives O(n).

Analogy

A talent show with 3 chairs for finalists. When a new act beats the weakest finalist, the weakest one leaves their chair. You only ever need to know who the weakest finalist is — that is the top of the min-heap.

Why it works

"A min-heap of size k always holds the k largest seen so far, and its root is the smallest of them. Any new number that is not bigger than the root cannot be in the top k, so polling it loses nothing. Each step is O(log k), so the whole pass is O(n log k)."

The template to remember

// k LARGEST -> min-heap of size k (flip the comparator for k smallest)
PriorityQueue<T> heap = new PriorityQueue<>(byScoreAscending);
for (T x : items) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();   // drop the weakest
}
// heap now holds the k best; heap.peek() is the kth best
Remember

Top k largest → min-heap of size k. Top k smallest → max-heap of size k. The top is the one you would throw out. Frequencies → count map first, then heap or buckets.

Common mistakes
  • Using a max-heap of all n items and polling k times: O(n + k log n) is fine, but O(n) memory — the size-k heap uses O(k).
  • Checking size() > k before offering: then the newcomer never gets compared.
  • Top K Frequent: putting raw numbers in the heap instead of comparing by count ((a, b) -> cnt.get(a) - cnt.get(b)).
  • Bucket array of size n instead of n + 1 — a number can appear n times.
  • Expecting the heap to come out sorted when you iterate it. Poll it if you need order.

  • Easy703. Kth Largest Element in a Stream — the first animation, kept as a class.
    Show solution

    The idea

    After every add, return the k-th largest number seen so far. The top-k pattern: keep a min-heap of size k holding the k largest. Its top is the smallest of the winners, which is the k-th largest. Any number smaller than the top can never matter again, so it is dropped. This is the first animation written as a class.

    Brute force first

    Keep every number in a sorted list and insert in order: O(n) per add.

    Step by step

    1. Fields: k and a PriorityQueue<Integer> (min-heap by default).
    2. Constructor: feed every starting number through add.
    3. add(val): offer; if size > k, poll the smallest; return peek().

    Java

    class KthLargest {
    private final int k;
    // min-heap of the k largest seen; top = k-th largest
    private final PriorityQueue<Integer> heap =
        new PriorityQueue<>();

    public KthLargest(int k, int[] nums) {
        this.k = k;
        for (int x : nums) add(x);
    }

    public int add(int val) {
        heap.offer(val);
        if (heap.size() > k) heap.poll(); // drop smallest
        return heap.peek();
    }
}

    Time O(log k) per add · Space O(k) — the heap never holds more than k+1 numbers.

    Dry run

    k=3, nums 4 5 8 2   heap {4,5,8}  (2 was dropped)
add 3   {3,4,5,8} -> drop 3   top 4
add 5   {4,5,5,8} -> drop 4   top 5
add 10  drop 5 -> {5,8,10}    top 5
add 9   drop 5 -> {8,9,10}    top 8

    Watch out

    The heap is a min-heap even though we want the largest numbers: the top must be the weakest winner so it can be kicked out. The starting array may have fewer than k numbers.

  • Medium215. Kth Largest Element in an Array — size-k min-heap (or quickselect).
    Show solution

    The idea

    Find the k-th largest element of an unsorted array (duplicates count: [3,2,3,1,2,4,5,5,6], k=4 → 4). Same size-k min-heap: push each number, pop when the heap holds more than k. At the end the top is the answer. Quickselect is the O(n)-average alternative.

    Brute force first

    Sort and return nums[n - k]: O(n log n). Fine as a first answer; interviewers then ask for better.

    Step by step

    1. Empty min-heap.
    2. For each number: offer it; if size > k, poll.
    3. Return peek().

    Java

    class Solution {
    public int findKthLargest(int[] nums, int k) {
        PriorityQueue<Integer> heap = new PriorityQueue<>();
        for (int x : nums) {
            heap.offer(x);
            if (heap.size() > k) {
                heap.poll();     // keep only the k biggest
            }
        }
        return heap.peek();   // smallest of the k biggest
    }
}

    Time O(n log k) · Space O(k) — n heap operations, heap never above k+1.

    Dry run

    [3,2,1,5,6,4], k=2
3 {3}   2 {2,3}   1 {1,2,3}->drop 1   5 -> drop 2 {3,5}
6 -> drop 3 {5,6}   4 -> drop 4 {5,6}    top 5

    Watch out

    k-th largest means index n - k in ascending order, not k - 1. Quickselect (partition like quicksort, recurse into one side) averages O(n) but is O(n²) on bad pivots unless you pick them randomly.

  • Medium347. Top K Frequent Elements — the second animation.
    Show solution

    The idea

    Return the k values that appear most often: [1,1,1,2,2,3], k=2 → [1,2]. Two steps: count with a HashMap, then pick the top k by count with a min-heap of size k ordered by count; the least frequent of the kept ones sits on top and is pushed out when something more frequent arrives.

    Brute force first

    Sort the distinct values by count: O(m log m) for m distinct values. Bucket sort by count (index = frequency) is the O(n) alternative.

    Step by step

    1. Count every number in a map.
    2. For each (value, count) entry: offer the value into a min-heap that compares by count; if size > k, poll.
    3. Pour the heap into the result array.

    Java

    class Solution {
    public int[] topKFrequent(int[] nums, int k) {
        Map<Integer, Integer> count = new HashMap<>();
        for (int x : nums) count.merge(x, 1, Integer::sum);

        // min-heap by count: least frequent kept on top
        PriorityQueue<Integer> heap = new PriorityQueue<>(
            (a, b) -> Integer.compare(count.get(a),
                                      count.get(b)));
        for (int v : count.keySet()) {
            heap.offer(v);
            if (heap.size() > k) heap.poll();
        }
        int[] res = new int[k];
        for (int i = 0; i < k; i++) res[i] = heap.poll();
        return res;
    }
}

    Time O(n log k) · Space O(n) — counting is O(n); m ≤ n heap operations on a heap of size k.

    Dry run

    counts {1:3, 2:2, 3:1}, k=2
offer 1 {1}   offer 2 {2,1}   offer 3 {3,2,1} -> drop 3
result [2,1] (any order)

    Watch out

    The heap must compare counts, not the numbers themselves. The answer may be in any order; it is unique by the problem's guarantee.

  • Medium973. K Closest Points to Origin — k smallest distances → max-heap of size k.
    Show solution

    The idea

    The k closest points to the origin are the k smallest distances, so flip the top-k trick: keep a max-heap of size k. Its top is the farthest of the kept points; when the heap grows past k, that one goes. Compare x² + y² (no square root needed).

    Brute force first

    Sort all points by distance and return the first k: O(n log n).

    Step by step

    1. Max-heap whose comparator puts the larger squared distance first.
    2. Offer each point; if size > k, poll.
    3. Return the heap's contents.

    Java

    class Solution {
    public int[][] kClosest(int[][] points, int k) {
        // max-heap by distance: top = farthest kept
        PriorityQueue<int[]> heap = new PriorityQueue<>(
            (a, b) -> Integer.compare(dist(b), dist(a)));
        for (int[] p : points) {
            heap.offer(p);
            if (heap.size() > k) {
                heap.poll();           // drop farthest
            }
        }
        return heap.toArray(new int[0][]);
    }

    private int dist(int[] p) {
        // squared distance; sqrt keeps the same order
        return p[0] * p[0] + p[1] * p[1];
    }
}

    Time O(n log k) · Space O(k) — each point costs one heap operation on a heap of size k.

    Dry run

    [[3,3],[5,-1],[-2,4]], k=2    dist 18, 26, 20
add 18        {18}
add 26        {26,18}
add 20        {26,20,18} -> drop 26
answer [3,3] and [-2,4]

    Watch out

    "k smallest → max-heap, k largest → min-heap" is the rule to remember; mixing them up keeps the wrong end. x*x + y*y fits in int for coordinates up to 104.

  • Medium692. Top K Frequent Words — tie-break alphabetically in the comparator.
    Show solution

    The idea

    Return the k most frequent words, sorted by frequency (high first), and alphabetically when counts tie. ["i","love","leetcode","i","love","coding"], k=2 → ["i","love"]. Count, keep a size-k min-heap whose "weakest" word is on top: lower count is weaker, and for equal counts the alphabetically later word is weaker. Pop the heap and reverse at the end.

    Brute force first

    Sort all distinct words with the comparator (count desc, then word asc) and take k: O(m log m).

    Step by step

    1. Count words in a map.
    2. Heap comparator: if counts differ, smaller count first; else b.compareTo(a) (later word first).
    3. Offer each word; if size > k, poll.
    4. Poll everything into a list (weakest first), then reverse it.

    Java

    class Solution {
    public List<String> topKFrequent(String[] words,
                                     int k) {
        Map<String, Integer> count = new HashMap<>();
        for (String w : words) {
            count.merge(w, 1, Integer::sum);
        }

        // top of heap = weakest: lower count, or later word
        PriorityQueue<String> heap = new PriorityQueue<>(
            (a, b) -> {
                int ca = count.get(a), cb = count.get(b);
                if (ca != cb) {
                    return Integer.compare(ca, cb);
                }
                return b.compareTo(a);
            });
        for (String w : count.keySet()) {
            heap.offer(w);
            if (heap.size() > k) heap.poll();
        }
        List<String> res = new ArrayList<>();
        while (!heap.isEmpty()) res.add(heap.poll());
        Collections.reverse(res);        // strongest first
        return res;
    }
}

    Time O(n log k) · Space O(n) — counting plus one heap operation per distinct word.

    Dry run

    counts i:2 love:2 leetcode:1 coding:1, k=2
heap keeps i and love; ties among count 1 drop
pop order: love, i   reverse -> [i, love]

    Watch out

    The tie-break is reversed inside the heap (b.compareTo(a)) because the heap's top is the one to throw away. Forgetting the final reverse returns the answer back to front.

  • Medium658. Find K Closest Elements — heap works; binary search on the window is faster.
    Show solution

    The idea

    In a sorted array, return the k numbers closest to x, in ascending order (ties go to the smaller number). The answer is always a contiguous window of length k. Binary search for its left edge lo in [0, n-k]: compare x - arr[mid] with arr[mid+k] - x; if the left end is farther, the window should start later.

    Brute force first

    A max-heap of size k by distance (ties by value) works in O(n log k), or sort by distance in O(n log n).

    Step by step

    1. lo = 0, hi = n - k.
    2. While lo < hi: mid = (lo+hi)/2.
    3. If x - arr[mid] > arr[mid+k] - x, the left end loses: lo = mid + 1. Else hi = mid.
    4. Return arr[lo .. lo+k-1].

    Java

    class Solution {
    public List<Integer> findClosestElements(int[] arr,
                                             int k, int x) {
        int lo = 0, hi = arr.length - k;  // window start
        while (lo < hi) {
            int mid = (lo + hi) / 2;
            // window [mid, mid+k): drop left end or right?
            if (x - arr[mid] > arr[mid + k] - x) {
                lo = mid + 1;       // left end is worse
            } else {
                hi = mid;           // right end is worse
            }
        }
        List<Integer> res = new ArrayList<>();
        for (int i = lo; i < lo + k; i++) res.add(arr[i]);
        return res;
    }
}

    Time O(log(n − k) + k) · Space O(1) extra — binary search for the start, then copy k items.

    Dry run

    [1,2,3,4,5], k=4, x=3      lo 0, hi 1
mid 0: x-arr[0]=2, arr[4]-x=2 -> not greater, hi=0
lo = 0 -> [1,2,3,4]

    Watch out

    Compare signed differences, not Math.abs: with [1,1,2,2,2,2,2,3,3], k = 3, x = 3, absolute values stop at [2,2,2] instead of [2,3,3]. Using > (not >=) keeps the smaller numbers on ties.

  • Hard239. Sliding Window Maximum — heap with lazy removal, or a monotonic deque.
    Show solution

    The idea

    For every window of size k sliding across the array, report its maximum: [1,3,-1,-3,5,3,6,7], k=3 → [3,3,5,5,6,7]. Keep a monotonic deque (double-ended queue) of indices whose values decrease from front to back. The front is the window's max. A new value removes smaller values from the back (they can never be a max again), and the front leaves once it slides out of the window.

    Brute force first

    Scan each window for its max: O(n·k). A max-heap of (value, index) with lazy removal (pop the top while its index is outside the window) gives O(n log n).

    Step by step

    1. For each index i: if the front index is i - k (just left the window), remove it from the front.
    2. While the back value is ≤ nums[i], remove it from the back.
    3. Add i at the back.
    4. Once i >= k - 1, the front index holds this window's max; record it.

    Java

    class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        int n = nums.length;
        int[] res = new int[n - k + 1];
        Deque<Integer> dq = new ArrayDeque<>(); // indices
        for (int i = 0; i < n; i++) {
            if (!dq.isEmpty() && dq.peekFirst() == i - k) {
                dq.pollFirst();            // slid out
            }
            while (!dq.isEmpty()
                    && nums[dq.peekLast()] <= nums[i]) {
                dq.pollLast();         // never a max now
            }
            dq.offerLast(i);
            if (i >= k - 1) {               // full window
                res[i - k + 1] = nums[dq.peekFirst()];
            }
        }
        return res;
    }
}

    Time O(n) · Space O(k) — each index enters and leaves the deque once.

    Dry run

    i  val  deque (values)   max
0  1    [1]
1  3    [3]
2  -1   [3,-1]           3
3  -3   [3,-1,-3]        3
4  5    [5]   (3 slid out, rest smaller)  5
5  3    [5,3]            5
6  6    [6]              6
7  7    [7]              7

    Watch out

    Store indices, not values, so you can tell when the front has left the window. Remove the expired front before reading the max.

Test yourself

You need the 5 smallest distances. Min-heap or max-heap, and of what size?

A max-heap of size 5. Its top is the largest of the 5 smallest — the one to throw out when a closer point arrives.

What is the time complexity of the size-k heap approach, and why is it better than sorting when k is small?

O(n log k). log k is tiny when k is small (log 10 ≈ 3), while sorting is O(n log n).

Why can the bucket approach for Top K Frequent be O(n)?

Frequencies are between 1 and n, so they can be array indices. Reading buckets from n down to 1 replaces sorting.
