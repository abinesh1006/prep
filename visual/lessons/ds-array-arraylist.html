Array & ArrayList

An array is one unbroken row of equal-sized boxes in memory, so the computer can jump straight to box number i. An ArrayList is that same array plus a size counter and a rule for getting a bigger array when it fills up.

Time to learn: about 1.5 hours · Prerequisites: Big-O

Use it when you need…
  • Read or write by position — a[i], list.get(i) — in O(1).
  • Add or remove at the end — list.add(x), list.remove(list.size() - 1) — in O(1) (amortized).
  • Fast scanning from left to right: the boxes sit next to each other, which the CPU cache loves.
  • A fixed number of counters (int[26] for letters) or a DP table.

In plain words

When you write new int[5], Java asks for one block of memory big enough for five ints (5 × 4 bytes) and remembers where the block starts. Every box has the same width, so the address of box i is simple arithmetic: start + i × width. No searching, no walking — one multiplication and one addition. That is why a[i] is O(1) no matter how big the array is.

The catch: an array's length is fixed when it is created. ArrayList hides that. It keeps an array that is usually a bit bigger than needed, plus a size counter that says how many boxes are really in use. When every box is full and you add one more, it makes a new array 1.5 times bigger, copies everything over, and carries on.

Analogy

An array is a row of numbered lockers in a corridor. To reach locker 37 you do not open lockers 0 to 36 — you know each locker is 30 cm wide, so you walk straight to 37 × 30 cm. An ArrayList is a club that rents a row of lockers. When all are taken, it rents a new row one and a half times as long somewhere else and moves everybody's things over in one go. Moving day is slow, but it happens rarely, and each move buys a lot of free lockers.

What it looks like in memory

First an int[]: the numbers themselves sit side by side. Then what an ArrayList<Integer> really holds: an array of references (arrows), each pointing to a separate Integer object somewhere else on the heap.

Watch the operations

1. get(i) — jump straight to the box

Reading box 3, box 0 or box 4 costs exactly the same: one bounds check and one address calculation.

2. add(x) — and what happens when the array is full

We start with capacity 4 so the growth shows up quickly (the real default is 10). Watch the copies counter.

3. Why "amortized O(1)" — the cost of every add, as bars

Each bar is the work one add did: 1 for a plain write, 1 + size when it also had to copy. Spikes are rare and get further apart.

4. add(i, x) — inserting in the middle shifts everything after it

Insert 15 at index 1. Every element from index 1 to the end must move one box to the right first, starting from the back so nothing is overwritten.

5. remove(i) — removing from the middle shifts everything left

Build it yourself

The version interviewers ask for: a generic growable array with add, add(i, x), get, set, remove. Tested against java.util.ArrayList with 20,000 random operations.

import java.util.Arrays;

// A growable array, like java.util.ArrayList.
public class MyArrayList<E> {
    private Object[] data = new Object[10]; // capacity
    private int size = 0;                   // slots used

    // Add at the end: O(1) amortized.
    public void add(E x) {
        if (size == data.length) grow();    // full?
        data[size++] = x;
    }

    // Insert at index i: shifts the tail right, O(n).
    public void add(int i, E x) {
        if (i < 0 || i > size)
            throw new IndexOutOfBoundsException(i);
        if (size == data.length) grow();
        // move data[i..size-1] one slot to the right
        System.arraycopy(data, i, data, i + 1, size - i);
        data[i] = x;
        size++;
    }

    // Read index i: O(1), address = base + i * width.
    @SuppressWarnings("unchecked")
    public E get(int i) {
        if (i < 0 || i >= size)
            throw new IndexOutOfBoundsException(i);
        return (E) data[i];
    }

    public E set(int i, E x) {
        E old = get(i);                     // checks i
        data[i] = x;
        return old;
    }

    // Remove index i: shifts the tail left, O(n).
    public E remove(int i) {
        E old = get(i);                     // checks i
        // move data[i+1..size-1] one slot to the left
        System.arraycopy(data, i + 1, data, i, size - i - 1);
        data[--size] = null;                // let GC free it
        return old;
    }

    public int size() { return size; }

    // New array 1.5x bigger, copy everything over: O(n).
    private void grow() {
        int cap = data.length + (data.length >> 1);
        data = Arrays.copyOf(data, Math.max(cap, 1));
    }
}

Why Object[] and a cast? Java cannot do new E[10] (generics are erased at run time), so the real ArrayList also stores Object[] and casts on the way out.

The real Java class

Arrays

  • An array is an object on the heap: a small header (about 16 bytes, which includes the length) followed by the elements. length is a field, not a method — a.length, but list.size() and s.length().
  • New arrays are filled with defaults: 0, false, '\u0000' or null.
  • Every access is bounds-checked; the JIT compiler removes the check inside simple loops where it can prove the index is safe.
  • int[][] is an array of row arrays, not one flat block. Rows can have different lengths, and each row is its own object.
  • Element sizes: byte/boolean 1, char/short 2, int/float 4, long/double 8, a reference usually 4 (compressed pointers on heaps under 32 GB).

java.util.ArrayList

  • Fields: transient Object[] elementData, int size, plus modCount inherited from AbstractList.
  • new ArrayList<>() starts with a shared empty array; the first add allocates capacity 10 (lazy since Java 8).
  • Growth: newCapacity = old + (old >> 1) — 10, 15, 22, 33, 49, … (Java 17+ computes it in ArraysSupport.newLength). Copying uses Arrays.copyOf, which calls the native System.arraycopy.
  • It never shrinks by itself. trimToSize() shrinks, ensureCapacity(n) or new ArrayList<>(n) pre-sizes so a known number of adds never copies.
  • Fail-fast iterators: every structural change bumps modCount; an iterator that sees it change throws ConcurrentModificationException. That is what happens when you call list.remove(x) inside a for-each loop. Use iterator.remove() or list.removeIf(...).
  • It implements the marker interface RandomAccess, telling algorithms like Collections.binarySearch that get(i) is fast. LinkedList does not.
  • Not thread-safe. Vector is the old synchronized version (also doubles instead of ×1.5); avoid both Vector and Collections.synchronizedList in new code unless you really share the list.
  • Arrays.asList(arr) is a fixed-size view backed by the array (add throws). List.of(...) (Java 9) is fully immutable and rejects null.
  • Java 21 (sequenced collections): getFirst(), getLast(), removeLast(), reversed(). addFirst exists too, but on ArrayList it is still an O(n) shift.

Why int[] beats ArrayList<Integer> — boxing

Generics only work with objects, so ArrayList<Integer> stores each number as an Integer object. Compared with int[]:

  • Memory: about 4 bytes per element in int[] versus about 20 (4-byte reference + 16-byte object) — five times more.
  • Speed: every read follows a pointer to a different place in memory (a likely cache miss), and every add(5) may allocate a new object (autoboxing calls Integer.valueOf).
  • Correctness traps: == compares references. Integer.valueOf caches −128..127, so a.get(0) == a.get(1) is true for 100 and false for 1000. Use .equals or unbox to int. Unboxing a null throws NullPointerException.

Rule of thumb in interviews: known size → int[]; unknown size or you must return a List → ArrayList<Integer>.

Why and when to use it

  • The default list in Java. Index access, appending, sorting (Arrays.sort, list.sort), binary search, and scanning are all as fast as they get.
  • int[] for counting (int[26] letters, int[128] ASCII), prefix sums, DP tables, visited flags (boolean[]), and union-find parents.
  • ArrayList as a stack when you only touch the end (backtracking: path.add(x) … path.remove(path.size() - 1)).
  • Building results of unknown length that you must return as a List.

When not to use it

  • Many inserts/removes at the front → use ArrayDeque (O(1) at both ends).
  • "Is x in here?" asked many times → use a HashSet (O(1) instead of O(n)).
  • Always need the smallest/largest → PriorityQueue; need sorted order with inserts → TreeMap/TreeSet.
  • Inserts in the middle while walking with an iterator, at huge scale → a linked structure can win, but measure first (see Linked list).

Used in these patterns

  • Arrays & hashing — int[26] counters; Prefix sum — the pre[] array.
  • Two pointers, Sliding window, In-place tricks, Kadane — O(1) index access from both ends.
  • Binary search, Binary search on the answer, Rotated array — jumping to the middle needs random access.
  • Merge sort, Quick sort, Matrix traversal, Strings & palindromes (char[]).
  • DP intro, Grid DP, Knapsack, Advanced DP — the dp table.
  • Backtracking, Permutations — ArrayList path, add and remove at the end.
  • Heap, Union-find, Segment tree & Fenwick — trees stored inside an array.
  • Graph basics — adjacency list List<List<Integer>>.
Remember

Address = start + i × width → O(1) index. Full? New array ×1.5, copy all → add is O(1) amortized. Middle insert/remove shifts → O(n). Known size of numbers → int[], not ArrayList<Integer>.

Common mistakes
  • list.remove(1) on a List<Integer> removes index 1, not the value 1. For the value: list.remove(Integer.valueOf(1)).
  • Comparing boxed values with ==: works up to 127 by luck, fails at 128.
  • Removing inside a for-each loop → ConcurrentModificationException. Use removeIf or an explicit iterator.
  • list.add(0, x) in a loop: O(n) each, O(n²) total. Add at the end and reverse once, or use ArrayDeque.
  • Calling add on Arrays.asList(...) or List.of(...) → UnsupportedOperationException.
  • new ArrayList<>(n) sets capacity, not size — get(0) still throws. To get n zeros use new int[n] or new ArrayList<>(Collections.nCopies(n, 0)).
  • Arrays.fill(new int[3][3], …) or new ArrayList[n] filled with the same list object: every row is shared.

Interview questions on the internals

Why is array access O(1) but linked-list access O(n)?

Array boxes are equal-sized and contiguous, so the address of box i is computed (start + i × width) in one step. A linked list's nodes are scattered; the only way to find node i is to follow i next-pointers from the head.

What exactly happens when an ArrayList is full and you call add?

grow() computes a new capacity of old + old/2, allocates a new array, copies every element with System.arraycopy, swaps the field to the new array, then writes the element. The old array becomes garbage.

Prove that add is amortized O(1).

With growth factor 1.5, the copies happen at sizes c, 1.5c, 2.25c, … up to n. That is a geometric series whose sum is at most about n / (1.5 − 1) = 2n. So n adds cost n writes + at most ~2n copies = O(n) total, O(1) per add on average.

Why grow by a factor (×1.5 or ×2) and not by a fixed +10?

Adding a constant k means a copy every k adds: n/k copies of average size n/2 → O(n²) total, O(n) per add. Only multiplying keeps the total linear. Java picks 1.5 over 2 to waste less spare memory.

Is the capacity ever reduced when you remove elements?

No. remove and clear keep the big array. Call trimToSize() if the memory matters.

Why does ArrayList<Integer> use so much more memory than int[]?

Each element is a separate Integer object (~16 bytes) plus a 4-byte reference in the array, versus 4 bytes inline. It also costs a pointer hop per read, which hurts cache performance.

What is the difference between capacity and size?

Capacity is the length of the internal array (boxes available). Size is how many boxes hold real elements. Only indexes below size are valid.

Why does removing in a for-each loop throw ConcurrentModificationException?

The iterator remembers modCount. list.remove increments it; on the next next() the iterator sees the mismatch and fails fast instead of skipping or repeating elements.

How do you delete many elements from an ArrayList efficiently?

removeIf(pred) or a write-pointer pass (keep the elements you want at write++, then cut the tail) — one O(n) pass instead of O(n) per removal.
