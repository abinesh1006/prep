Linked list

A chain of separate little objects, each holding a value and the address of the next one. Adding or removing a link is cheap once you are standing at the right place — but getting to that place means walking the chain.

Time to learn: about 1.5 hours · Prerequisites: Array & ArrayList, Big-O

Use it when you need…
  • O(1) insert or remove at a node you already hold — no shifting, just re-pointing two or four arrows.
  • O(1) add/remove at both ends (a doubly linked list with head and tail).
  • To move a node from the middle to the end in O(1) — the heart of an LRU cache.
  • In interviews: whenever the problem hands you a ListNode head.

In plain words

An array keeps its values in one block, side by side. A linked list does not. Every value lives in its own small object called a node, created wherever the memory allocator found room. To keep them in order, each node stores a reference to the next node. The list itself only remembers the first node, the head. The last node's next is null.

A singly linked list has only next. A doubly linked list also has prev, so you can walk backwards and unlink a node without knowing who points at it. A sentinel (dummy) node is a fake node that always sits at the front (and often another at the back), so the list is never truly empty and the code never has to ask "is this the head?".

Analogy

A treasure hunt. Each clue tells you where the next clue is hidden. Slipping a new clue into the middle is easy — rewrite one clue to point at the new one, and make the new one point onward. But to reach clue number 50 you must visit clues 1 to 49 in order; you cannot jump. An array is a numbered row of lockers; a linked list is a treasure hunt.

What it looks like in memory

Watch the operations

1. addFirst on a singly linked list — O(1), no shifting

2. get(i) — you must walk, but Java walks from the nearer end

No address arithmetic is possible, so finding index i means following arrows. A doubly linked list can start from whichever end is closer.

3. Insert after a node — four pointer writes

We already hold node p (the 3) and insert 5 after it. Watch the order: the new node is wired up first, then the neighbours are switched over.

4. Unlink a node — two pointer writes

5. Why arrays scan faster: cache locality

The CPU never reads one number from RAM; it loads a whole cache line (64 bytes) at a time. Below, each row is one cache line of memory. Count the slow trips to RAM (cache misses).

Build it yourself

A doubly linked list of ints with head and tail sentinels — the exact shape used inside an LRU cache. Tested against java.util.LinkedList with 20,000 random operations.

import java.util.NoSuchElementException;

// Doubly linked list with two sentinel (dummy) nodes.
public class MyLinkedList {
    private static class Node {
        int val;
        Node prev, next;
        Node(int val) { this.val = val; }
    }

    private final Node head = new Node(0); // sentinel
    private final Node tail = new Node(0); // sentinel
    private int size = 0;

    public MyLinkedList() {
        head.next = tail;                  // empty list:
        tail.prev = head;                  // H <-> T
    }

    public void addFirst(int v) { linkAfter(head, v); }
    public void addLast(int v) { linkAfter(tail.prev, v); }

    // Insert v at index i (0..size): O(n) find, O(1) link.
    public void add(int i, int v) {
        if (i < 0 || i > size)
            throw new IndexOutOfBoundsException(i);
        linkAfter(i == size ? tail.prev : node(i).prev, v);
    }

    public int get(int i) { return node(i).val; }

    public int removeFirst() {
        if (size == 0) throw new NoSuchElementException();
        return unlink(head.next);
    }

    public int removeLast() {
        if (size == 0) throw new NoSuchElementException();
        return unlink(tail.prev);
    }

    public int size() { return size; }

    // Four pointer writes. No null checks thanks to sentinels.
    private void linkAfter(Node p, int v) {
        Node n = new Node(v);
        n.prev = p;
        n.next = p.next;
        p.next.prev = n;
        p.next = n;
        size++;
    }

    // Two pointer writes: neighbours skip over n.
    private int unlink(Node n) {
        n.prev.next = n.next;
        n.next.prev = n.prev;
        size--;
        return n.val;
    }

    // Walk from the nearer end: at most size/2 hops.
    private Node node(int i) {
        if (i < 0 || i >= size)
            throw new IndexOutOfBoundsException(i);
        Node cur;
        if (i < size / 2) {
            cur = head.next;
            for (int k = 0; k < i; k++)
                cur = cur.next;
        } else {
            cur = tail.prev;
            for (int k = size - 1; k > i; k--)
                cur = cur.prev;
        }
        return cur;
    }
}

On LeetCode you rarely build a whole list class — you get a bare ListNode (val, next) and write functions over it. The same sentinel trick applies there: ListNode dummy = new ListNode(0); dummy.next = head; so deleting the first node is no special case, then return dummy.next.

The real Java class

  • java.util.LinkedList<E> is a doubly linked list. Fields: Node<E> first, Node<E> last, int size. Node: E item; Node<E> next; Node<E> prev.
  • It uses no sentinels: first and last are null when empty, so methods like linkLast and unlink are full of if (prev == null) branches. Our sentinel version shows why dummy nodes are popular.
  • get(i) calls node(i), which walks from first if i < (size >> 1), else from last — exactly the animation above.
  • It implements both List and Deque: addFirst/addLast/pollFirst/pollLast/peekFirst/peekLast are O(1). It accepts null elements (ArrayDeque does not).
  • It does not implement RandomAccess. Collections.binarySearch on it falls back to iterator walking.
  • The only way to get O(1) insert/remove in the middle is through a ListIterator you already moved there (it.add(x), it.remove()). list.add(i, x) still walks to i first: O(n).
  • Iterators are fail-fast (modCount), like ArrayList. Java 21 adds reversed() via SequencedCollection.
  • Inside the JDK, linked nodes appear where O(1) relinking matters: LinkedHashMap threads a doubly linked list through its entries (LRU order), and HashMap buckets are singly linked chains.

Why it is rarely the right choice in Java

Big-O says a linked list wins at front/middle inserts. Real machines disagree more often than not:

  • Front/back operations: ArrayDeque also does them in O(1), with no node allocation and contiguous memory. It beats LinkedList as both stack and queue.
  • Middle inserts: you first have to find the spot (O(n) walk, full of cache misses). ArrayList.add(i, x) also costs O(n), but its shift is one System.arraycopy — a fast bulk memory move. For lists up to many thousands of elements, ArrayList usually wins.
  • Memory: ~40 bytes per Integer element vs ~20 in ArrayList and 4 in int[]; more garbage-collector work.
  • Even Joshua Bloch, who wrote LinkedList, has said he never uses it.

Where linked nodes do win: when you keep a direct reference to a node (from a HashMap) and must move or delete it in O(1) — LRU and LFU caches, and interview problems built on ListNode.

Why and when to use it

  • The problem gives you ListNode: reversing, merging, finding the middle, detecting a cycle — the list is the input.
  • You hold references to nodes and need O(1) move-to-front / unlink: LRU cache (HashMap<key, Node> + doubly linked list with sentinels).
  • Splicing whole chains in O(1) (merge two sorted lists by re-pointing, not copying).

When not to use it

  • As a stack or queue → ArrayDeque.
  • As a general list, or anything with index access → ArrayList.
  • For "remove from the middle by value" → a HashSet or TreeSet finds it in O(1)/O(log n) instead of walking.
  • For an LRU cache in real code → LinkedHashMap with access order already does it (see HashMap). Interviewers still often ask you to build it by hand.

Used in these patterns

  • Reverse a linked list — re-point every next with prev/cur/next.
  • Fast & slow pointers — middle node, cycle detection.
  • Merge lists — dummy head + splice; k lists with a heap.
  • LRU cache and Design problems — HashMap to nodes + doubly linked list with sentinels.
  • Graph basics — adjacency lists are lists of neighbours (an ArrayList in Java is the better choice).
Remember

Holding the node → O(1) relink. Finding the node → O(n) walk. Doubly + sentinels = no null checks. In Java, LinkedList loses to ArrayList and ArrayDeque almost every time because of cache misses and memory; linked nodes shine when a HashMap hands you the node.

Common mistakes
  • Wrong order of pointer writes: doing p.next = n first loses the old p.next forever. Wire the new node first, change the old neighbours last.
  • Forgetting to update prev in a doubly linked list — forward walks look fine, backward walks break.
  • No dummy node, then a special case for "delete the head" that you forget. Use dummy.next = head.
  • Losing the rest of the list during reversal: save next = cur.next before changing cur.next.
  • for (int i = 0; i < list.size(); i++) list.get(i) on a LinkedList: each get walks, so the loop is O(n²). Use for-each.
  • while (cur.next != null) when cur itself may be null → NullPointerException. Check the right one.

Interview questions on the internals

Singly vs doubly linked list — what does the extra pointer buy?

Walking backwards, and O(1) removal of a node you hold (it knows its predecessor). Cost: one more reference per node and two extra writes per insert.

What is a sentinel node and why use one?

A dummy node that is always present at the front (and/or back). Every real node then has a real predecessor and successor, so insert and delete need no null checks or head/tail special cases.

Is java.util.LinkedList singly or doubly linked? Does it use sentinels?

Doubly linked, with first and last fields and no sentinels (they are null when the list is empty).

How does LinkedList.get(i) find the node?

It walks from first if i < size/2, otherwise from last backwards. So at most n/2 hops, still O(n).

Insertion in the middle is O(1) for a linked list and O(n) for an array. Why is ArrayList still usually faster?

The O(1) assumes you already hold the node; finding it is an O(n) walk with a cache miss per hop. ArrayList's O(n) shift is one contiguous memory move, which the CPU does extremely fast. Plus LinkedList allocates a node per insert.

What is cache locality?

The CPU loads memory in 64-byte lines and prefetches sequential addresses. Data that is contiguous (arrays) gets mostly cache hits; data reached through pointers to random addresses (linked nodes) gets a miss per access.

Which Java collection should you use for a queue or stack, and why not LinkedList?

ArrayDeque: O(1) at both ends using a circular array, no per-element node objects, better cache behaviour. LinkedList works but is slower and uses more memory.

How would you build an O(1) LRU cache?

A HashMap<key, Node> for O(1) lookup plus a doubly linked list with sentinels in recency order. On get, unlink the node and re-add it at the front; on put over capacity, unlink tail.prev and remove its key from the map. Or extend LinkedHashMap with access order.

How do you delete a node from a singly linked list when you are given only that node (not the head)?

Copy the next node's value into it and unlink the next node: node.val = node.next.val; node.next = node.next.next;. It does not work for the last node.
