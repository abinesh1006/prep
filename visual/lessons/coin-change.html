Coin Change

For every amount from 0 up to the target, work out the answer once — using the answers for smaller amounts you already have.

Time to learn: about 2 hours · Prerequisites: DP intro

When to use it — the signal

You have a set of item sizes you may use any number of times (coins, stamps, square numbers, words) and a target total. "Fewest coins to make amount", "number of ways to make amount", "can it be made at all". This is the unbounded knapsack family.

The idea in plain words

Coins [1, 2, 5], amount 7. Greedy ("take the biggest coin first") happens to work here, but not always: with coins [1, 3, 4] and amount 6, greedy takes 4+1+1 (3 coins) while 3+3 needs only 2. So we must try every option — cleverly.

Think about the last coin you put down. If it was a 2, then the rest was the best way to make 7 − 2 = 5. So:

dp[a] = 1 + min(dp[a − 1], dp[a − 2], dp[a − 5]) — "fewest coins for amount a".

  • dp[0] = 0: making 0 needs no coins.
  • Fill a = 1, 2, 3 … 7 in order; every cell only looks at smaller amounts, already filled.
  • An amount that cannot be made stays at "infinity" (we use amount + 1), and the answer becomes −1.

Counting ways (Coin Change II) is the same table with + instead of min — but the order of the two loops decides whether you count combinations (1+2 and 2+1 are the same) or orderings (they are different).

Analogy

A shop assistant who keeps a cheat sheet: "fewest coins for 1 cent, 2 cents, 3 cents…". To give 7 cents, they look at three lines of the sheet — 6, 5 and 2 cents — add one coin to the best one, and write the 7-cent line down for next time.

Watch it work

1. Fewest coins

Coins [1, 2, 5], amount 7. The labels under the table point at the cells each new cell depends on (amount minus each coin); the green one is the winner.

2. Number of ways — coins in the outer loop

Coins [1, 2, 5], amount 5. dp[a] = number of ways to make a. We process one coin type at a time: after the pass for coin 1, dp counts ways using only 1s; after coin 2, ways using 1s and 2s; and so on.

3. Why loop order matters — the wrong order counts orderings

Swap the loops (amount outside, coins inside) and you count sequences: 1+2 and 2+1 become two different ways. Coins [1, 2], amount 3: the right answer is 2 (1+1+1, 1+2), but this order gives 3.

Why it works

"Every way to make amount a ends with some last coin c, and what comes before it is a way to make a − c. Since a − c < a, filling amounts in increasing order means those answers are ready. For counting, putting coins in the outer loop fixes the order in which coin types appear, so each combination is counted exactly once."

The template to remember

// fewest items: min over the last item
for (int a = 1; a <= T; a++) for (int c : coins)
    if (c <= a) dp[a] = Math.min(dp[a], dp[a - c] + 1);
// count combinations: coins OUTSIDE
for (int c : coins) for (int a = c; a <= T; a++) dp[a] += dp[a - c];
// count orderings: amount OUTSIDE
for (int a = 1; a <= T; a++) for (int c : coins) if (c <= a) dp[a] += dp[a - c];
Remember

Last coin → look back by each coin. Min coins: any loop order. Count ways: coins outside = combinations, amount outside = orderings.

Common mistakes
  • Using Integer.MAX_VALUE as infinity and then adding 1 — it overflows to a negative number. Use amount + 1.
  • Forgetting to return −1 when the amount cannot be made (coins [2], amount 3).
  • dp[0] = 0 in the counting version — it must be 1, or every count stays 0.
  • Trying greedy (biggest coin first): fails for coins [1, 3, 4], amount 6.

Test yourself

Coins [2], amount 3 — what does the table hold at the end?

dp = [0, ∞, 1, ∞]. dp[3] is still "infinity" (4), so the answer is −1.

Why does the inner loop in Coin Change II start at a = c?

An amount smaller than the coin cannot end with that coin, and a − c would be negative.

Is the loop order important for the min-coins version?

No. A minimum does not care about order — both loop orders give the same result. Order only matters when counting.
