Monotonic Deque

A double-ended queue that keeps its values in falling (or rising) order, so the best value of a moving window is always waiting at the front.

Time to learn: about 2 hours · Prerequisites: Sliding window, Monotonic stack, Prefix sum

When to use it — the signal

"Maximum (or minimum) of every window of size k", "max minus min in a window ≤ limit", "shortest subarray with sum at least K" when numbers can be negative, or a DP where dp[i] depends on the best dp[j] for j in the last k positions.

The idea in plain words

A deque (say "deck", double-ended queue) lets you add and remove at both ends in O(1). In Java: ArrayDeque with offerLast, pollLast, peekFirst, pollFirst.

For the window maximum, we store indices in the deque, with their values falling from front to back. When a new number arrives, every smaller number at the back is useless: the new number is bigger and stays in the window longer, so those smaller ones can never be the maximum again. Pop them.

The front is the biggest number still in the window. If its index has slid out of the window (index ≤ i − k), pop it from the front.

Each index is pushed once and popped at most once, so the whole scan is O(n) — compared with O(n·k) for scanning every window, or O(n log k) with a heap.

Analogy

A queue of job applicants where a stronger, younger applicant arrives: everyone weaker and older standing behind in line just goes home — they will never be picked while the newcomer is around. The person at the front is the best one, until they retire (leave the window).

Watch it work

1. Sliding Window Maximum (k = 3)

2. Shortest Subarray with Sum at Least K (negatives allowed)

Plain sliding window breaks when numbers can be negative (growing the window can make the sum smaller). Instead use prefix sums P: the sum of nums[i..j−1] is P[j] − P[i]. We want the closest i before j with P[j] − P[i] ≥ K. Keep start indices in a deque with rising P values. Here nums = [2, −1, 2, 3], K = 4.

Why it works

"An element that is smaller than a newer element can never be the window maximum again, because the newer one is bigger and leaves later — so dropping it loses nothing. Every index is pushed and popped at most once, which gives O(n)." For the K problem: "a later start with a smaller-or-equal prefix sum is better in every way, and once a start has produced an answer, later ends can only make it longer."

The template to remember

Deque<Integer> dq = new ArrayDeque<>();   // indices
for (int i = 0; i < n; i++) {
    if (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst(); // expired
    while (!dq.isEmpty() && worse(dq.peekLast(), i)) dq.pollLast(); // useless
    dq.offerLast(i);
    if (i >= k - 1) use(dq.peekFirst());    // front = best
}
Remember

Front = best, and leaves when too old. Back = newest; it kicks out everyone worse before it joins. Store indices, not values.

Common mistakes
  • Storing values instead of indices — then you cannot tell when the front has left the window.
  • Using < instead of <= when popping the back: duplicates pile up (still correct, but slower to reason about).
  • Using a plain sliding window for "sum ≥ K" with negative numbers — it gives wrong answers; use prefix sums + deque.
  • Using Stack or LinkedList — ArrayDeque is the fast, standard choice.

Test yourself

Why is the sliding window maximum O(n) even though there is a while loop inside the for loop?

Each index is pushed exactly once and popped at most once, so across the whole run the while loop does at most n pops in total.

For the window minimum, what changes?

Keep values rising from front to back: pop the back while it is ≥ the new value.

Why can we pop the front in the "sum ≥ K" problem after recording it?

That start already gave its shortest possible answer with the current end j; any later end would make the subarray longer, so it is no longer useful.
