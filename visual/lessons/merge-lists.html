Merge Sorted Lists

Build the answer behind a dummy node: keep taking the smaller front node and hooking it onto the tail. For k lists, let a min-heap tell you which front is smallest.

Time to learn: about 1.5 hours · Prerequisites: Reverse a linked list, Merge sort, Heap

When to use it — the signal

"Merge two / k sorted lists (or arrays)", "combine sorted streams", "sort a linked list", "k-th smallest across k sorted rows", "smallest range covering k lists". Sorted inputs + one sorted output = merge.

The idea in plain words

Two lists: 1 → 2 → 4 and 1 → 3 → 4. The smallest node of the answer is one of the two fronts. Take it, hook it to the answer, and the next front of that list moves up. Repeat. When one list runs out, hook the rest of the other list on in one go — it is already sorted.

The dummy node is a fake first node (value doesn't matter). Without it, the very first hook is a special case ("the answer is empty, so this node becomes the head"). With it, every hook is the same: tail.next = node; tail = node;. At the end the real answer is dummy.next.

K lists: comparing k fronts each time costs k per node. Instead, put the k fronts into a min-heap (a structure that hands you its smallest item in O(log k)). Pop the smallest, hook it on, push that node's follower. Total O(N log k) for N nodes.

Analogy

Several checkout queues where everyone is sorted by ticket number, merging into one exit door. A guard looks only at the person at the front of each queue and waves through the lowest ticket. With many queues, the guard keeps a little sorted notepad of just the front tickets (the heap) so he never has to scan all queues.

Why it works

"Every list is sorted, so the smallest remaining node overall is always one of the current fronts. Taking it never blocks a smaller node later. Two lists: compare the two fronts, O(m + n). K lists: a min-heap of the k fronts gives the smallest in O(log k), so O(N log k)."

The template to remember

ListNode dummy = new ListNode(0), tail = dummy;
while (a != null && b != null) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else { tail.next = b; b = b.next; }
    tail = tail.next;
}
tail.next = (a != null) ? a : b;
return dummy.next;
// k lists: heap of fronts; poll, hook, push poll.next
Remember

Dummy + tail, smaller front wins, hook the leftovers. K lists: heap of fronts → O(N log k).

Common mistakes
  • Forgetting tail = tail.next — every node overwrites the same link.
  • Looping over the leftovers one by one — just one assignment tail.next = rest.
  • Comparator a.val - b.val can overflow for big negative/positive values; use Integer.compare.
  • Pushing null heads into the heap (empty lists) → NullPointerException.
  • Merging k lists one after another into a growing result: O(N·k). Use a heap or pair them up (divide and conquer).

Test yourself

What does the dummy node save you from?

The special case of the first node: without it you must check "is the answer still empty?" before every hook. With it, tail always exists.

Why is the heap size never more than k?

It holds at most one node per list — the current front. Each poll is followed by at most one push from the same list.

Without a heap, how else can you merge k lists in O(N log k)?

Divide and conquer: merge lists in pairs (1+2, 3+4, …), then pairs of results, for log k rounds, each round O(N).
