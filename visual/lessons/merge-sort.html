Merge Sort

Cut the array in half again and again until every piece has one number, then zip the pieces back together in order — always O(n log n).

Time to learn: about 2 hours · Prerequisites: Recursion, Two pointers, Big-O

When to use it — the signal

"Sort in guaranteed O(n log n)", "stable sort" (equal items keep their order), "sort a linked list", "count inversions" / "count smaller numbers after self", or any time you must merge two sorted things.

The idea in plain words

Sorting 8 numbers is hard. Sorting 1 number is free — it is already sorted. Merge sort uses that:

  • Split: cut [38, 27, 43, 3, 9, 82, 10, 15] into two halves of 4, cut those into 2s, then into 1s. Three rounds of cutting (8 → 4 → 2 → 1, because log₂ 8 = 3).
  • Merge: two sorted piles can be combined into one sorted pile by repeatedly taking the smaller of the two front items. [27, 38] and [3, 43]: take 3, then 27, then 38, then 43.
  • Merge the 1s into sorted 2s, the 2s into sorted 4s, the 4s into the sorted 8.

Each round of merging touches every number once (n work), and there are log n rounds, so the total is O(n log n) — even in the worst case. The cost: merging needs a spare array of size n (O(n) extra memory).

Analogy

Two teachers each hold a stack of exam papers already sorted by roll number. To combine them, you look at the top paper of each stack, take the smaller roll number, put it face down on the new pile, and repeat. You never need to look deeper than the two top papers.

Watch it work

The whole sort, level by level. Each box is one piece of the array. First the pieces are split down to single numbers, then merged back up. (The real code does this depth-first through recursion, but every merge happens exactly as shown.)

Now zoom into one merge: combining the sorted halves [3, 27, 38, 43] and [9, 10, 15, 82]. Pointer i walks the left half, j the right half, k is where the next number is written.

Why it works

"Merging two sorted arrays is linear: the smallest remaining item is always at one of the two fronts. Splitting halves the size each level, so there are log n levels of O(n) merging — O(n log n) in every case, with O(n) extra space, and it is stable."

The template to remember

void sort(int[] a, int lo, int hi) {   // [lo, hi)
    if (hi - lo < 2) return;
    int mid = lo + (hi - lo) / 2;
    sort(a, lo, mid); sort(a, mid, hi);
    merge(a, lo, mid, hi);   // take the smaller front, copy leftovers
}

Arrays need a temporary buffer to merge; linked lists do not, which is why merge sort is the natural sort for lists (148).

Remember

Split to 1s, merge by "smaller front wins". log n levels × n work = O(n log n), always. Stable. O(n) extra space.

Common mistakes
  • Forgetting the leftover loops — the tail of one half never gets copied.
  • Using < instead of <= in the merge: still sorted, but no longer stable.
  • Allocating the temp array inside every call is fine for interviews, but say you could allocate it once and pass it down.
  • Mixing [lo, hi] and [lo, hi) ranges — pick half-open and stick to it.

Practice in this order

  • Easy88. Merge Sorted Array — the merge step, filled from the back.
    Show solution

    The idea

    nums1 has m real numbers and n empty slots at the end; nums2 has n numbers; both are sorted. Merge nums2 into nums1 in place. If we filled from the front we would overwrite numbers we still need, so fill from the back: the biggest remaining number goes into the last empty slot. This is the merge step of merge sort, run backwards.

    Brute force first

    Copy nums2 into the empty slots and sort the whole array. O((m+n) log(m+n)).

    Step by step

    1. Point i at the last real number of nums1 (m - 1), j at the last of nums2 (n - 1), and k at the last slot (m + n - 1).
    2. While j >= 0 (nums2 still has numbers):
    3. If i >= 0 and nums1[i] > nums2[j], put nums1[i] at k and move i left.
    4. Otherwise put nums2[j] at k and move j left.
    5. Move k left. Leftover nums1 numbers are already in place.

    Java

    class Solution {
    public void merge(int[] nums1, int m, int[] nums2, int n) {
        int i = m - 1, j = n - 1, k = m + n - 1;
        while (j >= 0) {
            // bigger of the two tails goes to the back
            if (i >= 0 && nums1[i] > nums2[j])
                nums1[k--] = nums1[i--];
            else
                nums1[k--] = nums2[j--];
        }
    }
}

    Time O(m + n) · Space O(1) — each number is placed once, in place.

    Dry run

    nums1 = [1,2,3,0,0,0], nums2 = [2,5,6]
k=5: 3 vs 6 -> 6   [1,2,3,0,0,6]
k=4: 3 vs 5 -> 5   [1,2,3,0,5,6]
k=3: 3 vs 2 -> 3   [1,2,3,3,5,6]
k=2: 2 vs 2 -> 2 (from nums2), j done -> [1,2,2,3,5,6]

    Watch out

    Loop on j >= 0, not on both pointers: once nums2 is used up, the rest of nums1 is already correct. Check i >= 0 before reading nums1[i] (case m = 0).

  • Easy21. Merge Two Sorted Lists — same merge on linked lists.
    Show solution

    The idea

    Two sorted linked lists, one sorted result. Look at the two front nodes, take the smaller, and repeat; when one list runs out, attach the rest of the other. A dummy head node (a fake first node) means we never need a special case for the first link.

    Step by step

    1. Make a dummy node and a tail pointer at it.
    2. While both lists have nodes, link the smaller front node after tail, move that list forward, and move tail forward.
    3. Attach whichever list is not empty to tail.next.
    4. Return dummy.next.

    Java

    class Solution {
    public ListNode mergeTwoLists(ListNode a, ListNode b) {
        ListNode dummy = new ListNode(0); // fake head
        ListNode tail = dummy;
        while (a != null && b != null) {
            if (a.val <= b.val) { tail.next = a; a = a.next; }
            else { tail.next = b; b = b.next; }
            tail = tail.next;
        }
        tail.next = (a != null) ? a : b; // the leftover
        return dummy.next;
    }
}

    Time O(n + m) · Space O(1) — we relink existing nodes, no new ones besides the dummy.

    Dry run

    a = 1-2-4, b = 1-3-4
1(a) 1(b) 2(a) 3(b) 4(a) | a empty, attach b's 4
result 1-1-2-3-4-4

    Watch out

    Forgetting the leftover attach loses the tail of the longer list. Using <= takes from the first list on ties, which keeps the merge stable (equal values keep their order).

  • Medium912. Sort an Array — write merge sort from memory.
    Show solution

    The idea

    Sort in O(n log n) without built-in sort. Merge sort: split the array in half, sort each half the same way, then merge the two sorted halves by repeatedly taking the smaller front item. A half of size 1 is already sorted, which stops the splitting.

    Brute force first

    Bubble or insertion sort is O(n²) and times out on 5 · 104 numbers.

    Step by step

    1. Make one helper array tmp of size n, reused by every merge.
    2. sort(lo, hi): if the range has one item, return. Otherwise mid = (lo + hi) / 2, sort [lo, mid], sort [mid+1, hi].
    3. Merge: i walks the left half, j the right half; copy the smaller into tmp; then copy the leftovers.
    4. Copy tmp[lo..hi] back into nums.

    Java

    class Solution {
    private int[] tmp;

    public int[] sortArray(int[] nums) {
        tmp = new int[nums.length];
        sort(nums, 0, nums.length - 1);
        return nums;
    }

    private void sort(int[] a, int lo, int hi) {
        if (lo >= hi) return; // 0 or 1 item: sorted
        int mid = lo + (hi - lo) / 2;
        sort(a, lo, mid);
        sort(a, mid + 1, hi);
        merge(a, lo, mid, hi);
    }

    // merge sorted a[lo..mid] and a[mid+1..hi]
    private void merge(int[] a, int lo, int mid, int hi) {
        int i = lo, j = mid + 1, k = lo;
        while (i <= mid && j <= hi)
            tmp[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];
        while (i <= mid) tmp[k++] = a[i++];
        while (j <= hi) tmp[k++] = a[j++];
        for (k = lo; k <= hi; k++) a[k] = tmp[k];
    }
}

    Time O(n log n) · Space O(n) — log n levels of splitting, each level merges n items; plus the helper array.

    Dry run

    [5,2,3,1]
split  [5,2] [3,1] -> [5][2] [3][1]
merge  [2,5] [1,3]
merge  1 (right) 2 (left) 3 (right) 5 (left) -> [1,2,3,5]

    Watch out

    Allocate tmp once, not inside every merge, or the many small allocations slow it down a lot. Quick sort also works here but needs a random pivot (see the quick sort lesson); merge sort is always O(n log n).

  • Medium148. Sort List — merge sort on a linked list (find middle with fast/slow).
    Show solution

    The idea

    Sort a linked list in O(n log n). Linked lists cannot jump to an index, but merge sort only needs two things that lists do well: find the middle (slow pointer moves 1, fast moves 2; when fast reaches the end, slow is in the middle) and merge two sorted lists. Split, sort each half, merge.

    Brute force first

    Copy the values into an array, sort it, write them back. O(n log n) time but O(n) extra space, and interviewers want the list version.

    Step by step

    1. If the list has 0 or 1 nodes, it is sorted: return it.
    2. Find the middle: slow = head, fast = head.next; move slow 1 and fast 2 until fast runs out.
    3. Cut the list after slow: right = slow.next, slow.next = null.
    4. Sort both halves recursively.
    5. Merge the two sorted halves with a dummy head (problem 21).

    Java

    class Solution {
    public ListNode sortList(ListNode head) {
        if (head == null || head.next == null) return head;
        // fast starts one ahead so slow stops at the
        // end of the left half
        ListNode slow = head, fast = head.next;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
        }
        ListNode right = slow.next;
        slow.next = null; // cut into two lists
        return merge(sortList(head), sortList(right));
    }

    private ListNode merge(ListNode a, ListNode b) {
        ListNode dummy = new ListNode(0), tail = dummy;
        while (a != null && b != null) {
            if (a.val <= b.val) { tail.next = a; a = a.next; }
            else { tail.next = b; b = b.next; }
            tail = tail.next;
        }
        tail.next = (a != null) ? a : b;
        return dummy.next;
    }
}

    Time O(n log n) · Space O(log n) — the recursion is log n deep; nodes are relinked, not copied.

    Dry run

    4-2-1-3
middle: slow=2 -> left 4-2, right 1-3
4-2 -> 4 | 2 -> merge 2-4
1-3 -> 1 | 3 -> merge 1-3
merge 2-4 with 1-3 -> 1-2-3-4

    Watch out

    Start fast at head.next, not head: with two nodes, starting at head leaves slow on the second node, the left half never shrinks, and the recursion never ends. Remember to cut with slow.next = null.

  • Hard315. Count of Smaller Numbers After Self — count during the merge.
    Show solution

    The idea

    For each number, count how many numbers to its right are smaller. For [5,2,6,1] the answer is [2,1,1,0]. Run merge sort on the indexes. While merging a left half with a right half, a right-half item that is taken before a left item is smaller and was to its right. So when a left item is placed, add the number of right items already placed. Pattern: count during the merge.

    Brute force first

    For each i, scan all j > i and count nums[j] < nums[i]. O(n²), too slow for 105.

    Step by step

    1. Keep an array idx of original positions and sort it by value with merge sort, so we always know where a number came from.
    2. In the merge, keep rightTaken = how many right-half items have been copied so far.
    3. If the right item is smaller than the left item, copy it and do rightTaken++.
    4. Otherwise copy the left item and add rightTaken to its count: exactly those right items are smaller and came after it.
    5. Leftover left items also get rightTaken added.

    Java

    class Solution {
    private int[] count, idx, tmp;

    public List<Integer> countSmaller(int[] nums) {
        int n = nums.length;
        count = new int[n];
        idx = new int[n];
        tmp = new int[n];
        for (int i = 0; i < n; i++) idx[i] = i;
        sort(nums, 0, n - 1);
        List<Integer> res = new ArrayList<>();
        for (int c : count) res.add(c);
        return res;
    }

    // sorts idx[lo..hi] by nums value
    private void sort(int[] nums, int lo, int hi) {
        if (lo >= hi) return;
        int mid = lo + (hi - lo) / 2;
        sort(nums, lo, mid);
        sort(nums, mid + 1, hi);
        int i = lo, j = mid + 1, k = lo;
        int rightTaken = 0; // smaller items from the right
        while (i <= mid && j <= hi) {
            if (nums[idx[j]] < nums[idx[i]]) {
                rightTaken++;
                tmp[k++] = idx[j++];
            } else {
                count[idx[i]] += rightTaken;
                tmp[k++] = idx[i++];
            }
        }
        while (i <= mid) {
            count[idx[i]] += rightTaken;
            tmp[k++] = idx[i++];
        }
        while (j <= hi) tmp[k++] = idx[j++];
        for (k = lo; k <= hi; k++) idx[k] = tmp[k];
    }
}

    Time O(n log n) · Space O(n) — normal merge sort plus a constant amount of work per copy. A Fenwick tree (binary indexed tree) over the values also solves it in O(n log n).

    Dry run

    nums = [5,2,6,1]
merge [5] [2]: 2 < 5 -> rightTaken=1; place 5: count[5] += 1
merge [6] [1]: 1 < 6 -> rightTaken=1; place 6: count[6] += 1
merge [2,5] [1,6]: 1 first (rightTaken=1);
  place 2: +1, place 5: +1; then 6
counts: 5->2, 2->1, 6->1, 1->0  => [2,1,1,0]

    Watch out

    Use strict < when deciding to take the right item: equal numbers are not "smaller", so on a tie take the left one first. Sorting the values directly loses track of where each came from, which is why we sort indexes.

  • Hard493. Reverse Pairs — count pairs across halves before merging.
    Show solution

    The idea

    Count pairs i < j with nums[i] > 2 · nums[j]. Use merge sort: once both halves are sorted, every pair with i in the left and j in the right can be counted with two pointers, because as the left value grows, the number of right values it beats can only grow. Count first, then merge as usual.

    Brute force first

    Check every pair. O(n²), too slow for 5 · 104 numbers.

    Step by step

    1. Merge sort the array; the answer is pairs inside the left half + pairs inside the right half + pairs across.
    2. For the cross pairs (both halves already sorted): set j = mid + 1. For each left item i, move j forward while nums[i] > 2 · nums[j].
    3. Add j - (mid + 1): that many right items are small enough for nums[i].
    4. Then merge the halves normally.

    Java

    class Solution {
    private int[] tmp;

    public int reversePairs(int[] nums) {
        tmp = new int[nums.length];
        return sort(nums, 0, nums.length - 1);
    }

    private int sort(int[] a, int lo, int hi) {
        if (lo >= hi) return 0;
        int mid = lo + (hi - lo) / 2;
        int cnt = sort(a, lo, mid) + sort(a, mid + 1, hi);
        // both halves sorted: count cross pairs
        int j = mid + 1;
        for (int i = lo; i <= mid; i++) {
            while (j <= hi && a[i] > 2L * a[j]) j++;
            cnt += j - (mid + 1);
        }
        // normal merge
        int i = lo, k = lo;
        j = mid + 1;
        while (i <= mid && j <= hi)
            tmp[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];
        while (i <= mid) tmp[k++] = a[i++];
        while (j <= hi) tmp[k++] = a[j++];
        for (k = lo; k <= hi; k++) a[k] = tmp[k];
        return cnt;
    }
}

    Time O(n log n) · Space O(n) — the counting pass is linear per level, like the merge.

    Dry run

    nums = [1,3,2,3,1]
left [1,3,2] -> no pair inside (3 > 2*2 is false) -> 0
right [3,1]  -> 3 > 2*1 -> 1 pair
cross: left sorted [1,2,3], right sorted [1,3]
  1: none, 2: none, 3 > 2*1 -> 1
total 0 + 1 + 1 = 2

    Watch out

    2 * nums[j] overflows int when values are near 231; write 2L * a[j]. Count before merging, while the two halves are still separate.

Test yourself

Why is merge sort O(n log n) even on the worst input?

It always splits exactly in half, whatever the values are, so there are always log n levels, each costing O(n).

What does "stable" mean and why does merge sort have it?

Equal items keep their original order. On a tie the merge takes from the left half first (<=), and left items came first originally.

Why is merge sort the best choice for sorting a linked list?

It only walks forward and re-links nodes, so merging needs no extra array (O(log n) stack only), and it does not need random access like quick sort's partition.
