Merge Sort

Cut the array in half again and again until every piece has one number, then zip the pieces back together in order — always O(n log n).

Time to learn: about 2 hours · Prerequisites: Recursion, Two pointers, Big-O

When to use it — the signal

"Sort in guaranteed O(n log n)", "stable sort" (equal items keep their order), "sort a linked list", "count inversions" / "count smaller numbers after self", or any time you must merge two sorted things.

The idea in plain words

Sorting 8 numbers is hard. Sorting 1 number is free — it is already sorted. Merge sort uses that:

  • Split: cut [38, 27, 43, 3, 9, 82, 10, 15] into two halves of 4, cut those into 2s, then into 1s. Three rounds of cutting (8 → 4 → 2 → 1, because log₂ 8 = 3).
  • Merge: two sorted piles can be combined into one sorted pile by repeatedly taking the smaller of the two front items. [27, 38] and [3, 43]: take 3, then 27, then 38, then 43.
  • Merge the 1s into sorted 2s, the 2s into sorted 4s, the 4s into the sorted 8.

Each round of merging touches every number once (n work), and there are log n rounds, so the total is O(n log n) — even in the worst case. The cost: merging needs a spare array of size n (O(n) extra memory).

Analogy

Two teachers each hold a stack of exam papers already sorted by roll number. To combine them, you look at the top paper of each stack, take the smaller roll number, put it face down on the new pile, and repeat. You never need to look deeper than the two top papers.

Why it works

"Merging two sorted arrays is linear: the smallest remaining item is always at one of the two fronts. Splitting halves the size each level, so there are log n levels of O(n) merging — O(n log n) in every case, with O(n) extra space, and it is stable."

The template to remember

void sort(int[] a, int lo, int hi) {   // [lo, hi)
    if (hi - lo < 2) return;
    int mid = lo + (hi - lo) / 2;
    sort(a, lo, mid); sort(a, mid, hi);
    merge(a, lo, mid, hi);   // take the smaller front, copy leftovers
}
Remember

Split to 1s, merge by "smaller front wins". log n levels × n work = O(n log n), always. Stable. O(n) extra space.

Common mistakes
  • Forgetting the leftover loops — the tail of one half never gets copied.
  • Using < instead of <= in the merge: still sorted, but no longer stable.
  • Allocating the temp array inside every call is fine for interviews, but say you could allocate it once and pass it down.
  • Mixing [lo, hi] and [lo, hi) ranges — pick half-open and stick to it.

Test yourself

Why is merge sort O(n log n) even on the worst input?

It always splits exactly in half, whatever the values are, so there are always log n levels, each costing O(n).

What does "stable" mean and why does merge sort have it?

Equal items keep their original order. On a tie the merge takes from the left half first (<=), and left items came first originally.

Why is merge sort the best choice for sorting a linked list?

It only walks forward and re-links nodes, so merging needs no extra array (O(log n) stack only), and it does not need random access like quick sort's partition.
