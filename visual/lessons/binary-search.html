Binary Search

Look at the middle of a sorted list, decide which half cannot hold the answer, throw that half away, and repeat — a million items take only 20 looks.

Time to learn: about 2 hours · Prerequisites: Big-O, Two pointers

When to use it — the signal

The input is sorted (or "rotated sorted"), and the question says "find", "first position", "last position", "insert position", or demands O(log n). More generally: any yes/no question whose answers look like no no no yes yes yes as you move along.

The idea in plain words

You have 10 sorted numbers and want to know where 23 is. Checking them one by one takes up to 10 looks. Instead, look at the middle number, 16.

  • 16 is smaller than 23. The list is sorted, so everything left of 16 is even smaller — none of it can be 23. Throw away the left half in one go.
  • If the middle were bigger than 23, throw away the right half instead.
  • If the middle is 23, you are done.

Each look halves what is left: 10 → 5 → 2 → 1. A list of 1,000,000 numbers needs at most about 20 looks, because 220 ≈ 1,000,000. That is what O(log n) means: the work grows with the number of halvings, not with the size.

We keep two markers, lo and hi, around the part that might still hold the answer, and mid is the middle of that part.

Analogy

Finding a word in a paper dictionary. You open it near the middle, see "M", know "giraffe" comes earlier, and never look at the second half again. You open the middle of the first half, and so on, until you are on the right page.

Watch it work

Classic search: is the target in [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]? First target 23 (found), then target 10 (not found). Press ▶ or use the arrow keys to step.

Second flavour: first and last occurrence (lower bound)

With duplicates, [1, 3, 5, 5, 5, 5, 8, 9], plain search may land on any 5. Interviews usually ask for the first one (and the last). The trick: when nums[mid] >= target, do not stop — mid might be the first 5, or there might be another 5 to its left, so keep mid and search left (hi = mid). The search ends when lo and hi meet, on the first index whose value is >= target. This is called the lower bound.

Last occurrence = (lower bound of target + 1) − 1: the first number bigger than 5 sits right after the last 5.

Why lo + (hi - lo) / 2 and not (lo + hi) / 2?

A Java int holds at most 2,147,483,647. With a huge array, say lo = 1,500,000,000 and hi = 2,000,000,000, the sum lo + hi = 3,500,000,000 does not fit: it wraps round to a negative number, mid becomes negative, and the program crashes. hi - lo = 500,000,000 is small, half of it is 250,000,000, and lo + 250,000,000 = 1,750,000,000 always fits. Same middle, no overflow. (Java's own Arrays.binarySearch had this exact bug for 9 years.)

Why it works

"The array is sorted, so one comparison with the middle tells me a whole half cannot contain the answer. Every loop keeps the answer inside [lo, hi] and halves that range, so the loop runs O(log n) times."

The template to remember

// Lower bound: first index where ok(i) is true (half-open)
int lo = 0, hi = n;
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (ok(mid)) hi = mid;     // mid could be the answer
    else lo = mid + 1;     // answer is to the right
}
return lo;                 // n means "nowhere"

Binary search needs one thing from its structure: O(1) access to any position plus an order that tells you which half to throw away. A sorted array gives both.

Remember

Sorted → halve it. Exact match: lo <= hi, move to mid ± 1. First/last: lo < hi, hi = mid keeps the candidate.

Common mistakes
  • Mixing the two styles: while (lo < hi) with hi = mid - 1 skips answers; while (lo <= hi) with hi = mid loops forever.
  • (lo + hi) / 2 overflowing on big values — always write lo + (hi - lo) / 2.
  • Returning the lower bound without checking i < n && nums[i] == target — the target may not exist.
  • Binary searching an unsorted array. It silently gives wrong answers.

Practice in this order

  • Easy704. Binary Search — the first animation, exactly.
    Show solution

    The idea

    The array is sorted, so we can look at the middle item and throw away half the array every time. In [-1,0,3,5,9,12] looking for 9: the middle is 3, and 9 is bigger, so 9 can only be on the right. This is classic binary search: keep a range [lo, hi] that still might hold the target.

    Brute force first

    Scan every item from left to right until you find the target. That is O(n) and ignores that the array is sorted.

    Step by step

    1. Set lo = 0 and hi = n - 1: the whole array is still possible.
    2. While lo <= hi, take the middle mid = lo + (hi - lo) / 2.
    3. If nums[mid] is the target, return mid.
    4. If it is smaller than the target, the answer is to the right: lo = mid + 1.
    5. Otherwise it is to the left: hi = mid - 1.
    6. If the loop ends, the range is empty, so return -1.

    Java

    class Solution {
    public int search(int[] nums, int target) {
        int lo = 0, hi = nums.length - 1;
        while (lo <= hi) {
            // middle without (lo + hi) overflowing
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return mid;
            if (nums[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return -1; // range became empty
    }
}

    Time O(log n) · Space O(1) — each step halves the range and we only keep two indexes.

    Dry run

    nums = [-1,0,3,5,9,12], target = 9
lo=0 hi=5 mid=2 nums=3  < 9 -> lo=3
lo=3 hi=5 mid=4 nums=9 == 9 -> return 4

    Watch out

    Use lo <= hi (not <), or a one-item range is never checked. Move to mid + 1 / mid - 1, never to mid, or the loop can run forever.

  • Easy35. Search Insert Position — it is the lower bound.
    Show solution

    The idea

    We want the index where the target is, or where it would be inserted to keep the array sorted. That is the first index whose value is >= target, called the lower bound. In [1,3,5,6] with target 2, the first value >= 2 is 3 at index 1, so the answer is 1.

    Brute force first

    Walk from the left and return the first index with nums[i] >= target, or n if none. O(n).

    Step by step

    1. Search with lo = 0, hi = n. n is allowed because the target may go at the end.
    2. While lo < hi, take mid.
    3. If nums[mid] < target, mid is too small, so the answer is right of it: lo = mid + 1.
    4. Otherwise mid could be the answer: keep it with hi = mid.
    5. When lo == hi, that is the first index with value >= target.

    Java

    class Solution {
    public int searchInsert(int[] nums, int target) {
        int lo = 0, hi = nums.length; // answer in [lo, hi]
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < target) lo = mid + 1;
            else hi = mid; // mid may be the answer
        }
        return lo;
    }
}

    Time O(log n) · Space O(1) — a plain binary search on the boundary.

    Dry run

    nums = [1,3,5,6], target = 2
lo=0 hi=4 mid=2 nums=5 >= 2 -> hi=2
lo=0 hi=2 mid=1 nums=3 >= 2 -> hi=1
lo=0 hi=1 mid=0 nums=1 <  2 -> lo=1
lo=hi=1 -> return 1

    Watch out

    Start with hi = n, not n - 1: a target bigger than everything (7 in the example) must return 4.

  • Easy278. First Bad Version — first true in no no yes yes.
    Show solution

    The idea

    Versions look like good good good bad bad: once one is bad, all later ones are bad. We want the first bad one with as few calls to isBadVersion as possible. This is binary search for the first true: if mid is bad, the answer is mid or earlier; if mid is good, it is later.

    Brute force first

    Call isBadVersion(1), (2), ... until one is true. Up to n calls, O(n).

    Step by step

    1. Keep lo = 1, hi = n; the first bad version is somewhere in [lo, hi].
    2. While lo < hi, take mid.
    3. If mid is bad, the first bad is mid or before: hi = mid.
    4. If it is good, the first bad is after it: lo = mid + 1.
    5. When they meet, lo is the first bad version.

    Java

    public class Solution extends VersionControl {
    public int firstBadVersion(int n) {
        int lo = 1, hi = n;
        while (lo < hi) {
            // lo + hi can overflow when n is near 2^31
            int mid = lo + (hi - lo) / 2;
            if (isBadVersion(mid)) hi = mid; // keep mid
            else lo = mid + 1;
        }
        return lo;
    }
}

    Time O(log n) · Space O(1) — about 31 API calls even for n = 231 − 1.

    Dry run

    n = 5, first bad = 4
lo=1 hi=5 mid=3 good -> lo=4
lo=4 hi=5 mid=4 bad  -> hi=4
lo=hi=4 -> return 4

    Watch out

    (lo + hi) / 2 overflows when n is close to Integer.MAX_VALUE; that is the classic wrong answer here. Use lo + (hi - lo) / 2.

  • Medium34. Find First and Last Position — two lower bounds.
    Show solution

    The idea

    In a sorted array, all copies of the target sit next to each other. The first copy is the lower bound of target (first value >= target). The last copy is just before the lower bound of target + 1. In [5,7,7,8,8,10] with 8: first >= 8 is index 3, first >= 9 is index 5, so the answer is [3,4]. Pattern: two lower bounds.

    Brute force first

    Scan the array and remember the first and last index equal to the target. O(n), which misses the O(log n) the problem asks for.

    Step by step

    1. Write a helper lowerBound(x): the first index whose value is >= x (or n if none).
    2. first = lowerBound(target).
    3. If first == n or nums[first] != target, the target is missing: return [-1,-1].
    4. last = lowerBound(target + 1) - 1.
    5. Return [first, last].

    Java

    class Solution {
    public int[] searchRange(int[] nums, int target) {
        int first = lowerBound(nums, target);
        if (first == nums.length || nums[first] != target)
            return new int[]{-1, -1};
        // last copy is just before the first value > target
        int last = lowerBound(nums, target + 1) - 1;
        return new int[]{first, last};
    }

    // first index with nums[i] >= x, or n if none
    private int lowerBound(int[] nums, int x) {
        int lo = 0, hi = nums.length;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < x) lo = mid + 1;
            else hi = mid;
        }
        return lo;
    }
}

    Time O(log n) · Space O(1) — two binary searches.

    Dry run

    nums = [5,7,7,8,8,10], target = 8
lowerBound(8) = 3   (nums[3] = 8, found)
lowerBound(9) = 5   -> last = 4
answer [3,4]

    Watch out

    Empty array: lowerBound returns 0, which equals n, so check first == n before reading nums[first]. target + 1 is safe here because values are at most 109.

  • Medium74. Search a 2D Matrix — treat the matrix as one sorted array: row = i / cols, col = i % cols.
    Show solution

    The idea

    Each row is sorted and each row starts after the previous row ends, so reading the rows one after another gives one long sorted list of m · n numbers. Run normal binary search on positions 0 .. m·n − 1 and turn a position i into a cell with row = i / n, col = i % n. Pattern: binary search on a flattened index.

    Brute force first

    Check every cell: O(m · n). Or binary search each row: O(m log n).

    Step by step

    1. Let m = rows, n = columns; search positions lo = 0, hi = m * n - 1.
    2. Take mid and read the value at matrix[mid / n][mid % n].
    3. Equal to target: return true.
    4. Smaller: go right (lo = mid + 1); bigger: go left (hi = mid - 1).
    5. Range empty: return false.

    Java

    class Solution {
    public boolean searchMatrix(int[][] matrix, int target) {
        int m = matrix.length, n = matrix[0].length;
        int lo = 0, hi = m * n - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            // position -> cell
            int v = matrix[mid / n][mid % n];
            if (v == target) return true;
            if (v < target) lo = mid + 1;
            else hi = mid - 1;
        }
        return false;
    }
}

    Time O(log(m·n)) · Space O(1) — one binary search over all cells.

    Dry run

    matrix = [[1,3,5,7],[10,11,16,20],[23,30,34,60]]
target = 3, n = 4
lo=0 hi=11 mid=5 -> [1][1]=11 > 3 -> hi=4
lo=0 hi=4  mid=2 -> [0][2]=5  > 3 -> hi=1
lo=0 hi=1  mid=0 -> [0][0]=1  < 3 -> lo=1
lo=1 hi=1  mid=1 -> [0][1]=3  found -> true

    Watch out

    Divide and mod by the number of columns n, not rows. Mixing them up only fails on non-square matrices, so test one.

  • Medium162. Find Peak Element — not sorted, but "go uphill" still halves the range.
    Show solution

    The idea

    A peak is an item bigger than both neighbours; outside the array counts as minus infinity. The array is not sorted, but look at mid and its right neighbour: if the next item is higher, walking uphill to the right must reach a peak (the hill has to come down by the end). If it is lower, mid itself or something to its left is a peak. Pattern: binary search on a slope.

    Brute force first

    Scan for the first i with nums[i] > nums[i+1]; if none, the last index. O(n).

    Step by step

    1. Keep lo = 0, hi = n - 1; a peak is always inside [lo, hi].
    2. While lo < hi, take mid (it is always less than hi, so mid + 1 is safe).
    3. If nums[mid] < nums[mid + 1], we are going uphill: a peak is to the right, lo = mid + 1.
    4. Otherwise we are going downhill: mid could be the peak, hi = mid.
    5. When lo == hi, that index is a peak.

    Java

    class Solution {
    public int findPeakElement(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            // uphill: a peak is to the right
            if (nums[mid] < nums[mid + 1]) lo = mid + 1;
            else hi = mid; // downhill: mid may be it
        }
        return lo;
    }
}

    Time O(log n) · Space O(1) — each step drops half the range.

    Dry run

    nums = [1,2,1,3,5,6,4]
lo=0 hi=6 mid=3: 3 < 5 uphill   -> lo=4
lo=4 hi=6 mid=5: 6 > 4 downhill -> hi=5
lo=4 hi=5 mid=4: 5 < 6 uphill   -> lo=5
return 5 (value 6); index 1 would also be accepted

    Watch out

    Compare with mid + 1, not mid - 1: with lo < hi the middle rounds down, so mid + 1 always exists. A one-item array returns 0 without entering the loop.

Test yourself

How many looks does binary search need for 1,000 sorted items at most?

About 10, because 210 = 1,024. For a million items, about 20.

In the lower-bound version, why hi = mid and not hi = mid - 1?

Because nums[mid] >= target means mid itself may be the first match. mid - 1 would throw it away.

The target is missing. What does lower bound return, and what does it mean?

The index where the target would be inserted to keep the array sorted (possibly n). That is exactly LeetCode 35.

How do you count how many times x appears in a sorted array in O(log n)?

lowerBound(x + 1) - lowerBound(x).
