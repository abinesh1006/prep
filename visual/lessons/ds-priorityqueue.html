PriorityQueue: a binary heap in an array

Java's PriorityQueue is a tree that is stored as a plain array, with one rule: every parent is smaller than (or equal to) its children. That rule puts the smallest element at index 0 and makes add and remove O(log n).

Time to learn: about 1.5 hours · Prerequisites: Array & ArrayList, Tree recursion. The pattern lesson is Heap / priority queue.

Use it when you need…
  • the smallest (or largest) element again and again while elements keep arriving: peek O(1), poll and offer O(log n);
  • the top k of a stream without sorting everything: a heap of size k, O(n log k);
  • "process the cheapest next": Dijkstra, Prim, merge k sorted lists, task scheduling, meeting rooms.

In plain words

A sorted list would give you the minimum instantly, but keeping it sorted costs O(n) per insert (shifting). A heap is lazier: it is only partly sorted. It does not care about the order of brothers and cousins; it only promises that each parent is not bigger than its two children. That weaker promise is cheap to repair after a change, because a repair only walks one path from the root to a leaf, and a complete binary tree with n nodes is only about log₂ n levels tall.

The tree is never stored with pointers. The nodes are written level by level into an array, so the family links are just arithmetic:

  • parent of index i is (i - 1) / 2;
  • children of i are 2i + 1 and 2i + 2.
Analogy

A company org chart where every boss is more senior than the people right under them. The most senior person is always at the top. When a new hire turns out to be very senior, they swap with their boss again and again until they sit below someone more senior: they climb one chain, not the whole company. When the top person leaves, the most junior person is moved to the top seat and keeps stepping down under the more senior of their two reports until the rule holds again.

What it looks like in memory

The same six numbers, as the tree you think about and the array Java really stores. Level 0 is index 0, level 1 is indexes 1–2, level 2 is indexes 3–6.

Watch the operations

1. offer: add at the end, sift up (and grow when full)

Start with capacity 4 and offer 7, 4, 9, 2, 5, 1. Each new number lands in the first free slot (the next leaf, left to right) and then swaps with its parent while it is smaller.

2. poll: take the root, move the last leaf up, sift down

Poll twice from the heap built above. The root is the answer; the hard part is refilling the hole without breaking the shape.

3. The comparator, and the a - b overflow trap

A comparator returns a negative number if a should come first. (a, b) -> a - b looks right, but subtraction of two ints can overflow. Offer 1, then Integer.MIN_VALUE (shown as MIN), to a queue built with it.

4. No decrease-key: lazy deletion

Dijkstra wants to lower a node's distance when it finds a shorter path. PriorityQueue cannot change a priority in place (it would not know to sift), and remove(Object) is O(n). The standard trick: push a new entry and skip the old one when it comes out.

Build it yourself

The interview version: a min-heap of ints with offer, peek, poll. Tested against java.util.PriorityQueue with 300,000 random operations.

import java.util.Arrays;
import java.util.NoSuchElementException;

// A min-heap of ints in an array (what PriorityQueue does).
// Parent of i is (i - 1) / 2. Children are 2i + 1, 2i + 2.
class MinHeap {
    private int[] a = new int[4];
    private int size = 0;

    void offer(int x) {
        if (size == a.length)
            a = Arrays.copyOf(a, size * 2);   // grow
        a[size] = x;            // put it at the end
        siftUp(size++);         // then let it float up
    }

    int peek() {
        if (size == 0) throw new NoSuchElementException();
        return a[0];            // smallest is at the root
    }

    int poll() {
        if (size == 0) throw new NoSuchElementException();
        int min = a[0];
        a[0] = a[--size];       // last element to the root
        siftDown(0);            // then let it sink
        return min;
    }

    private void siftUp(int i) {
        while (i > 0) {
            int p = (i - 1) / 2;
            if (a[p] <= a[i]) break;   // in order
            swap(i, p);
            i = p;
        }
    }

    private void siftDown(int i) {
        while (2 * i + 1 < size) {     // has a left child
            int c = 2 * i + 1;
            if (c + 1 < size && a[c + 1] < a[c]) c++;
            if (a[i] <= a[c]) break;   // smaller than both
            swap(i, c);                // swap with smaller kid
            i = c;
        }
    }

    private void swap(int i, int j) {
        int t = a[i]; a[i] = a[j]; a[j] = t;
    }

    int size() { return size; }
}

For a max-heap flip the two comparisons (a[p] >= a[i], pick the larger child). For objects, take a Comparator<T> in the constructor and replace each < with cmp.compare(x, y) < 0.

The real Java class

  • Fields: Object[] queue, int size, Comparator comparator (null means natural order, so the elements must be Comparable, or you get ClassCastException on the second offer), modCount for fail-fast iterators.
  • Default capacity 11. Growth: if the capacity is under 64 it doubles + 2, otherwise it grows by 50%. The array never shrinks.
  • siftUp / siftDown are exactly the loops above, written as "hole" moves: instead of swapping at each level, Java keeps the moving element in a variable, slides parents (or children) into the hole, and writes the element once at the end. Same comparisons, fewer writes.
  • Building from a collection (new PriorityQueue<>(list)) runs heapify: siftDown from the last parent back to the root. That is O(n), faster than n offers (O(n log n)).
  • Iterator and toString are in array order, not sorted. To get sorted output, poll repeatedly (O(n log n)) or copy to a list and sort.
  • remove(Object) and contains are O(n): there is no index from value to position, so it scans. After finding index i, removeAt(i) moves the last element into i and sifts it down, or up if it did not move down: O(log n) for that part.
  • No decrease-key. If you change a field an element is compared by while it is inside the queue, the heap is silently broken. Remove and re-add (O(n)), or use lazy deletion (above).
  • No nulls (NullPointerException): poll() and peek() return null for empty. Not thread-safe: use PriorityBlockingQueue.
  • Ties are not stable: two equal elements can come out in any order. Add a tie-breaker (e.g. an index or timestamp) to the comparator if order matters.

Why and when to use it

  • Top k / k-th largest: a min-heap of size k; when it grows past k, poll the smallest. O(n log k) time, O(k) memory.
  • Merge k sorted lists: the heap holds one head per list; always poll the smallest.
  • Shortest paths (Dijkstra) and minimum spanning tree (Prim): always expand the cheapest frontier entry.
  • Scheduling: meeting rooms (min-heap of end times), task scheduler, CPU tasks by priority.
  • Running median: two heaps, a max-heap for the lower half and a min-heap for the upper half.

When not to use it

  • You need to remove or update arbitrary elements fast, or need both min and max: use a TreeMap / TreeSet (O(log n) remove, first and last).
  • You need the elements sorted once: just sort the array, O(n log n) with a better constant.
  • You need "is x present?": a HashSet is O(1); the heap is O(n).
  • The order is simply first come, first served: an ArrayDeque queue is O(1).
  • Priorities are small integers (0..k): an array of buckets (bucket queue) is O(1) per operation.
  • You want a single k-th element and can modify the array: quickselect is O(n) average (see Quick sort).

Used in these patterns

  • Heap / priority queue: the pattern lesson for this structure.
  • Top k and Two heaps (running median).
  • Merge lists: merge k sorted lists with a heap of heads.
  • Dijkstra, Shortest paths (advanced) and Minimum spanning tree (Prim): lazy deletion as above.
  • Intervals: meeting rooms with a min-heap of end times. Greedy: always take the best next choice.
Remember

Array heap: parent (i−1)/2, kids 2i+1 and 2i+2. offer = append + sift up, poll = last to root + sift down, both O(log n); peek O(1). Iteration is not sorted. remove(x) and contains(x) are O(n). No decrease-key: push again and skip stale entries. Compare with Integer.compare, never a - b.

Common mistakes
  • (a, b) -> a - b or b - a on values that can be large or negative: overflow silently corrupts the order. Use Integer.compare, Comparator.comparingInt, reverseOrder().
  • Expecting System.out.println(pq) or a for-each loop to show sorted order. Only poll() gives sorted order.
  • Forgetting a max-heap needs a comparator: new PriorityQueue<>() is always a min-heap.
  • Changing an element's priority field while it is inside the queue (e.g. editing dist inside the stored object). The heap does not notice.
  • Using pq.remove(x) inside a loop: O(n) each, so O(n²) total. Use lazy deletion or a TreeSet.
  • Top k largest with a max-heap of all n elements: O(n) memory and O(n log n). A min-heap of size k is the expected answer.
  • Putting int[] in a PriorityQueue without a comparator: arrays are not Comparable, so the second offer throws ClassCastException.

Interview questions on the internals

How is a PriorityQueue stored? Where are the children of index i?

As a complete binary tree written level by level into an array (Object[] queue). Children of i are at 2i + 1 and 2i + 2, the parent at (i − 1) / 2. The root, index 0, is the minimum.

Why is offer O(log n)?

The new element is placed in the next free leaf, so the tree stays complete and has height about log₂ n. Sift-up swaps it with its parent while it is smaller: at most one swap per level.

In poll, why move the last element to the root instead of promoting a child?

Removing the last slot keeps the tree complete (no gaps in the array). Then sift-down repairs the order along one path, always swapping with the smaller child so the new parent is smaller than both children.

Does iterating a PriorityQueue give sorted order?

No. The iterator and toString walk the array, which is only heap-ordered. Offering 5, 1, 4, 2, 3 prints [1, 2, 4, 5, 3]. Poll repeatedly to get sorted order.

What is wrong with (a, b) -> a - b?

Integer overflow. Integer.MIN_VALUE - 1 wraps to Integer.MAX_VALUE, so MIN looks bigger than 1. Use Integer.compare(a, b), which only compares.

What is the cost of remove(Object), and why?

O(n). The heap has no map from value to index, so it does a linear search. The fix afterwards (move the last element in, sift down or up) is O(log n).

Java's PriorityQueue has no decrease-key. How do you run Dijkstra with it?

Lazy deletion: when a distance improves, offer a new (node, distance) entry. When polling, skip entries whose distance is larger than the current best dist[node]. The heap holds at most E entries, so it is O(E log E) = O(E log V).

Building a heap from n elements: O(n log n) or O(n)?

n offers cost O(n log n), but bottom-up heapify (what new PriorityQueue<>(collection) does) is O(n): half the nodes are leaves and do not move, a quarter move at most one level, and the sum n/4·1 + n/8·2 + … is below n.

How do you get a max-heap?

new PriorityQueue<>(Comparator.reverseOrder()) or (a, b) -> Integer.compare(b, a). For objects: Comparator.comparingInt(Task::priority).reversed().
