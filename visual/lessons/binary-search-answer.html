Binary Search on the Answer

When you cannot search the array, search the answer: guess a value, check "does this work?", and halve the range of guesses.

Time to learn: about 2 hours · Prerequisites: Binary search, Big-O

When to use it — the signal

"Find the minimum speed / capacity / days / size such that it is possible", "minimize the maximum", "maximize the minimum", and the answer can be as large as 109. If you can write a quick feasible(x) that says yes or no, and bigger x never turns a yes into a no, this is the pattern.

The idea in plain words

Koko Eating Bananas: piles of [3, 6, 7, 9] bananas, and 8 hours. Each hour Koko picks one pile and eats up to k bananas from it (if the pile has fewer, she finishes it and waits for the next hour). What is the smallest k that lets her finish in 8 hours?

  • For any one speed, checking is easy: at k = 4 the piles take 1 + 2 + 2 + 3 = 8 hours. Yes, that works.
  • Faster is never worse: if k = 4 works, k = 5, 6, 7… work too. If k = 3 fails, k = 2 and 1 fail too.
  • So over the speeds 1 to 9 the answers look like no no no YES yes yes yes yes yes. We want the first yes — exactly what lower-bound binary search finds.

The array we search is not stored anywhere: it is the range of possible answers, 1 to the biggest pile. Each guess costs one O(n) check, and we need only log(range) guesses — about 30 even when piles hold a billion bananas.

Analogy

Choosing the cheapest phone plan that covers your data use. You do not try all 50 plans from the bottom. You try a middle plan: "enough?" Yes → maybe a cheaper one is enough too, look lower. No → look higher. A few tries and you have the cheapest plan that works.

Watch it work

First, the slow way: test every speed from 1 to 9, to see the yes/no shape. Each test adds up the hours per pile (a pile of p takes ⌈p / k⌉ hours, "⌈ ⌉" = round up).

Now the fast way: binary search over the speeds. Each guess runs the feasibility check pile by pile, then throws away half of the speeds.

Why it works

"feasible(k) is monotonic — once a speed works, every faster speed works — so the answers over the range form no…no yes…yes, and lower-bound binary search finds the first yes in O(n · log(max))."

The template to remember

int lo = smallestPossible, hi = largestPossible;
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (feasible(mid)) hi = mid;   // works: try smaller
    else lo = mid + 1;           // fails: go bigger
}
return lo;
// "maximize": flip it — find the last x that works
Remember

"Minimum x such that possible" → binary search x, write feasible(x). Range = [smallest sensible, largest sensible].

Common mistakes
  • Wrong range: for Ship Packages, lo must be the heaviest package (a smaller ship can never carry it), not 1.
  • Integer division instead of ceiling: use (p + k - 1) / k.
  • Summing hours in an int — with big inputs it overflows. Use long.
  • Checking that the problem is monotonic is skipped. If a bigger x can turn yes into no, this pattern does not apply.

Test yourself

What range do you search for Koko, and why is the top of it always feasible?

1 to max(piles). At speed max(piles) every pile takes exactly 1 hour, and h ≥ number of piles is guaranteed.

What is the time complexity for n piles with values up to M?

O(n log M): log M guesses, each an O(n) check.

How do you know a problem is "binary search on the answer" and not greedy or DP?

Ask "if x works, does every bigger (or smaller) x also work?" If yes, the answers are sorted yes/no and you can binary search them with a cheap check.
