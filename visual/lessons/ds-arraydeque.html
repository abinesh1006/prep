ArrayDeque: stack and queue in one

One plain array bent into a circle. Two indexes, head and tail, walk around it, so adding or removing at either end is O(1) and nothing ever shifts. This one class is the stack, the queue and the deque you should use in every Java interview.

Time to learn: about 1.5 hours · Prerequisites: Array & ArrayList, Stack basics

Use it when you need…
  • a stack (last in, first out): push, pop, peek in O(1);
  • a queue (first in, first out) for BFS: offer, poll, peek in O(1);
  • a deque: add or remove at both ends in O(1), e.g. the monotonic deque of sliding window maximum, or 0-1 BFS.

In plain words

An ArrayList is fast at its end but slow at its front: removing index 0 shifts every other element one place left, which is O(n). A queue removes from the front all the time, so an ArrayList is a bad queue.

The trick of ArrayDeque: never shift anything. Keep an index head (where the first element sits) and an index tail (the free slot just after the last element). Removing from the front just moves head one step right. Adding at the back writes at tail and moves it one step right.

When an index walks off the end of the array, it wraps around to index 0, like the hand of a clock going from 12 back to 1. That is why it is called a circular buffer (or ring buffer). The array only grows when every slot is really full.

Analogy

A round sushi conveyor with 8 plates. The chef puts new plates down at one spot (tail) and you take plates from another spot (head). Both spots move around the circle; no plate is ever pushed along. Only when every place on the belt is taken does the restaurant swap in a bigger belt and lay the plates out again in order.

What it looks like in memory

Capacity 8, five elements. The array (what the computer stores) and the queue order (what your code sees) are not the same picture: the queue starts at head = 5, runs to the end, and continues at index 0.

The index of the k-th element is (head + k) % capacity. That one formula is the whole idea.

Watch the operations

1. As a queue: offer at tail, poll at head, wrap around

Capacity 8. Offer 10 … 60, poll three times, then offer 70, 80, 90. Watch tail wrap from 7 back to 0 instead of the array growing.

2. As a stack: push is addFirst, head steps back and wraps

Java's Deque.push(x) is addFirst(x) and pop() is removeFirst(). So the top of the stack is the head. Starting at head 0, the first push moves head backwards, and 0 − 1 wraps to index 7.

3. Full: grow by doubling and unroll the circle

All 8 slots used, head = 5 (the queue wraps). One more offer. The array cannot simply be stretched: elements are copied into a new array twice as big, in queue order, so the copy starts at index 0 and nothing wraps any more.

4. One deque, both ends: the sliding-window-maximum move

The monotonic deque needs pollLast (throw away smaller values at the back) and pollFirst (drop the index that left the window). Both are O(1) on the circle. Window size 3 over [1, 3, 2, 5], storing indexes.

Build it yourself

Interviewers ask for this as "Design Circular Queue" (LeetCode 622) or "Design Circular Deque" (641). This version holds ints, keeps a size counter (simplest way to tell "empty" from "full", since both have head == tail) and doubles when full. Tested against java.util.ArrayDeque with 400,000 random operations.

import java.util.NoSuchElementException;

// A double-ended queue on a circular array.
class IntDeque {
    private int[] a = new int[8];
    private int head = 0;  // index of the first element
    private int tail = 0;  // index AFTER the last element
    private int size = 0;

    // step forward / back around the circle
    private int next(int i) { return (i + 1) % a.length; }
    private int prev(int i) {
        return (i - 1 + a.length) % a.length;
    }

    void addLast(int x) {          // queue: offer
        if (size == a.length) grow();
        a[tail] = x;
        tail = next(tail);
        size++;
    }

    void addFirst(int x) {         // stack: push
        if (size == a.length) grow();
        head = prev(head);
        a[head] = x;
        size++;
    }

    int pollFirst() {              // queue: poll, stack: pop
        if (size == 0) throw new NoSuchElementException();
        int x = a[head];
        head = next(head);
        size--;
        return x;
    }

    int pollLast() {
        if (size == 0) throw new NoSuchElementException();
        tail = prev(tail);
        size--;
        return a[tail];
    }

    int peekFirst() {
        if (size == 0) throw new NoSuchElementException();
        return a[head];
    }

    int peekLast() {
        if (size == 0) throw new NoSuchElementException();
        return a[prev(tail)];
    }

    int size() { return size; }
    boolean isEmpty() { return size == 0; }

    // Full: copy into a twice-as-big array, in order,
    // so the elements start again at index 0.
    private void grow() {
        int[] b = new int[a.length * 2];
        for (int i = 0; i < size; i++) {
            b[i] = a[(head + i) % a.length];
        }
        a = b;
        head = 0;
        tail = size;
    }
}

Why (i - 1 + a.length) % a.length and not (i - 1) % a.length? In Java, -1 % 8 is −1, not 7. Adding the length first keeps the number positive.

The real Java class

  • Fields: Object[] elements, int head, int tail. There is no size field: the size is computed from head and tail. To tell "full" from "empty" the array always keeps at least one slot empty, so the usable capacity is elements.length - 1.
  • Default capacity: new ArrayDeque<>() makes an array of 16 + 1 = 17 slots (Java 9+). In Java 8 the length was always a power of two (16) and wrapping used the bit trick (i + 1) & (length - 1) instead of %.
  • Growth (Java 9+): if the capacity is under 64 it roughly doubles (+2), otherwise it grows by 50%. The copy is done with two System.arraycopy calls (the part after head, then the wrapped part) rather than one element at a time. Java 8 always doubled.
  • No nulls. add(null), push(null), offer(null) all throw NullPointerException. A free slot is stored as null, and poll()/peek() return null to mean "empty", so a real null element would be impossible to tell apart. Removed slots are set back to null so the garbage collector can free the object.
  • Method names: stack: push = addFirst, pop = removeFirst, peek = peekFirst. Queue: offer = offerLast, poll = pollFirst, peek = peekFirst. The remove…/get…/element versions throw on empty; the poll…/peek… versions return null.
  • Iteration goes from head to tail: for a stack that is top first. Iterators are fail-fast (modifying while iterating throws ConcurrentModificationException on a best-effort basis).
  • Not thread-safe. For threads use ArrayBlockingQueue, LinkedBlockingDeque or ConcurrentLinkedDeque.

Why not java.util.Stack?

  • Stack extends Vector, and every Vector method is synchronized. You pay for a lock on every push and pop even with one thread.
  • Because it is a Vector, it exposes get(i), add(i, x), remove(i): anyone can reach into the middle and break "last in, first out".
  • It iterates (and prints) bottom first: push 1, 2, 3 prints [1, 2, 3], while an ArrayDeque used as a stack prints [3, 2, 1]. Surprising when you debug.
  • The Stack Javadoc itself says: use Deque<Integer> stack = new ArrayDeque<>(); instead.

Why not LinkedList as the queue?

  • LinkedList also implements Deque with O(1) ends, but every element is a separate Node object (item, next, prev, plus the object header: about 24 to 32 bytes extra per element) created on every add and left to the garbage collector on every remove.
  • The nodes are scattered in memory, so walking them misses the CPU cache. ArrayDeque's elements are side by side in one array. In practice ArrayDeque is usually several times faster.
  • LinkedList does allow null and is a List (index access in O(n)). If you need neither, ArrayDeque wins.

Why and when to use it

  • Any stack: valid parentheses, monotonic stack, iterative DFS, undo history.
  • Any queue: BFS on trees, grids and graphs, level order traversal, multi-source BFS, Kahn's topological sort.
  • Any deque: sliding window maximum (monotonic deque), 0-1 BFS (cost-0 edges go to the front, cost-1 to the back), palindrome checks from both ends.
  • Declare it by the interface: Deque<Integer> stack = new ArrayDeque<>(); and Queue<int[]> q = new ArrayDeque<>();.

When not to use it

  • You need the smallest / largest element first, not the oldest or newest: use a PriorityQueue.
  • You need to store null: use LinkedList (or better, a sentinel value).
  • Several threads share it: ArrayBlockingQueue (bounded, producer/consumer) or ConcurrentLinkedDeque.
  • You need index access or removal from the middle: ArrayList, or a TreeMap for sorted removal.
  • Hot loops on primitives where boxing hurts: an int[] with your own head/tail (exactly the class above) avoids Integer objects.

Used in these patterns

  • Stack basics and Monotonic stack: ArrayDeque as the stack.
  • Monotonic deque and Sliding window: both ends in one loop.
  • Tree BFS, Grid BFS / DFS, Multi-source BFS, Graph basics: the BFS queue.
  • Topological sort: Kahn's queue of in-degree 0 nodes.
  • Shortest paths (advanced): 0-1 BFS with addFirst / addLast.
  • Tree traversals: iterative in-order and pre-order with an explicit stack.
Remember

ArrayDeque = array + head + tail, wrapping with % capacity. Both ends O(1), grows by copying in queue order, no nulls. Stack: push / pop / peek. Queue: offer / poll / peek. Never Stack, rarely LinkedList.

Common mistakes
  • Using add on a deque you think of as a stack: add is addLast, but pop takes from the first. Mix push/pop or offer/poll, never add + pop.
  • queue.offer(null) or pushing a null child in tree BFS: NullPointerException. Check if (node.left != null) before offering.
  • Calling pop() / remove() on an empty deque throws NoSuchElementException; poll() returns null, which then crashes when auto-unboxed into an int. Check isEmpty() first.
  • In your own circular buffer, writing (i - 1) % n: Java's % keeps the sign, so it gives −1. Use (i - 1 + n) % n.
  • Telling empty from full with only head == tail: both look the same. Keep a size, or always leave one slot empty (what Java does).
  • Comparing two Integer values taken from the deque with ==: works up to 127 (cached), fails above. Use .equals or unbox to int.

Interview questions on the internals

How does ArrayDeque get O(1) removal at the front when ArrayList cannot?

It never shifts. It keeps a head index and just moves it forward one slot (wrapping around with modulo). ArrayList keeps its first element at index 0, so removing it shifts every element left: O(n).

With head == tail, is the buffer empty or full? How does Java know?

Both cases look the same. Either keep a size counter (common in interviews) or always leave one slot unused so head == tail only means empty. Java's ArrayDeque uses the second: capacity is length - 1, and it grows as soon as the last free slot would be used.

Why can't ArrayDeque hold null?

A null slot means "free", and poll()/peek() return null to mean "empty". Allowing null elements would make both ambiguous, so add(null) throws NullPointerException.

What happens to the order of elements when it grows?

It allocates a bigger array and copies the elements in logical order (from head, around the wrap, up to tail), so in the new array they are contiguous again and nothing wraps. Java does this with two System.arraycopy calls.

Why is java.util.Stack discouraged?

It extends Vector: every method is synchronized (lock cost with no benefit on one thread), it exposes index methods that break LIFO, and it iterates bottom first. Its own Javadoc recommends Deque/ArrayDeque.

ArrayDeque or LinkedList for a BFS queue?

ArrayDeque. Both are O(1) per operation, but LinkedList allocates a node per element (extra memory, garbage collection) and its nodes are scattered in memory (cache misses). ArrayDeque is one compact array. LinkedList only wins if you need nulls or the List interface.

Which end is the top when you use push/pop?

The front (head): push = addFirst, pop = removeFirst, peek = peekFirst. That is why printing the deque shows the top first.

Is add amortized O(1)? Explain.

Yes. A grow copies n elements but multiplies the room (doubling, or +50% for big arrays), so the next n or so adds are free. Spread over all adds, copying costs a constant per add.
