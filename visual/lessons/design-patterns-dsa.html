Data-Structure Design

"Design a class with these methods, each in O(1) (or O(log n))" — solved by gluing two simple structures together so each covers the other's weak spot.

Time to learn: about 3 hours · Prerequisites: Arrays and hashing, Stack basics, LRU cache, Binary search

When to use it — the signal

The question starts with "Design a ..." or "Implement the class ..." and lists methods with a required speed: "getMin in O(1)", "insert, delete and getRandom in average O(1)", "get the value at a timestamp", "number of hits in the past 5 minutes", "evict the least frequently used".

The idea in plain words

Write down each method and the speed it needs. Then ask: which single structure makes each method fast?

  • Hash map: find / insert / delete by key in O(1) — but no order and no "random element".
  • Array list: random index in O(1), add/remove at the end in O(1) — but finding a value is O(n).
  • Stack / queue / deque: O(1) at the ends; great when old items expire in order (time windows).
  • Sorted list + binary search: "the last value at or before time t" in O(log n).
  • Doubly linked list: move or remove a known node in O(1) (LRU, LFU).

When no single structure covers all methods, combine two and keep them in sync in every method. Example: RandomizedSet = array (for random) + map from value to index (for finding). Removing from the middle of an array is slow, so move the last element into the hole and remove the end instead.

Analogy

A library: books stand on shelves in a row (the array — easy to grab "a random book"), and the catalogue says which shelf slot each book is in (the map — easy to find a specific one). When a book leaves, the librarian moves the last book into the empty slot and fixes one catalogue card, instead of shifting the whole shelf.

Watch it work

2. Insert Delete GetRandom O(1) — array + map

3. Time-Based Key-Value Store — binary search on timestamps

Calls set("foo", v, t) arrive with increasing t, so each key's timestamps are already sorted. get("foo", t) = the value with the largest timestamp ≤ t.

4. Design Hit Counter — a queue of timestamps

Count hits in the past 300 seconds (5 minutes): a hit at time h counts at time t when h > t − 300.

LFU cache — the idea

LFU (Least Frequently Used) evicts the key that was used the fewest times; ties go to the least recently used among them. Both get and put must be O(1).

  • vals: key → value, and freq: key → how many times it was used.
  • buckets: frequency → a LinkedHashSet of keys with that frequency, in the order they were last used (oldest first). This is a small LRU list per frequency.
  • minFreq: the smallest frequency that has any keys.
  • On every use of a key with frequency f: move it from bucket f to bucket f + 1. If bucket f became empty and f was minFreq, then minFreq = f + 1.
  • On put of a new key when full: evict the first key of buckets[minFreq], then insert the new key with frequency 1 and set minFreq = 1.
void touch(int key) {                 // called by get and put
    int f = freq.get(key);
    freq.put(key, f + 1);
    buckets.get(f).remove(key);
    if (f == minFreq && buckets.get(f).isEmpty()) minFreq++;
    buckets.computeIfAbsent(f + 1, k -> new LinkedHashSet<>()).add(key);
}
// evict: int old = buckets.get(minFreq).iterator().next(); remove it everywhere

Why it works

"Each method's speed comes from one structure: the map answers 'where is x', the array answers 'give me a random one', the queue drops expired items from the front, the sorted list answers 'latest before t' by binary search. Every method updates both structures, so they never disagree."

The template to remember

// 1. List each method + required speed
// 2. Pick one structure per method:
//    find by key → HashMap      random → ArrayList
//    expire oldest → Deque      latest before t → sorted list + binary search
//    move/remove known item → doubly linked list (LinkedHashMap / LinkedHashSet)
// 3. Glue them; every method updates ALL of them
// Remove from the middle of an array in O(1):
list.set(i, last); pos.put(last, i); list.remove(list.size() - 1);
Remember

One structure per method, glued together and always updated together. Array + map for random; queue for time windows; binary search for "at time t"; buckets of LRU lists for LFU.

Common mistakes
  • RandomizedSet: forgetting to update the moved element's index in the map — or removing x from the map before reading its index. Also the case where x is the last element (the code above still works: it moves x onto itself, then removes it).
  • Min Stack with a single min variable — after popping the minimum you no longer know the next one.
  • Time map: binary searching for "== t" instead of "last ≤ t".
  • Hit counter: using < t − 300 instead of <= t − 300 — a hit exactly 300 seconds ago is out of the window.
  • LFU: forgetting to reset minFreq = 1 when a new key is inserted.

Test yourself

Why can RandomizedSet not use only a HashSet?

A HashSet cannot return a random element in O(1) — there is no index to pick. The array provides the index.

In the time map, why does appending keep the list sorted?

The problem guarantees set calls come with increasing timestamps, so every new time is the largest so far.

What does the Min Stack's mins stack hold after push 4, push 6, push 1?

[4, 4, 1] — the minimum of everything at or below each level.

In LFU, when does minFreq change?

It becomes f + 1 when the last key with frequency f = minFreq is used again, and it resets to 1 whenever a new key is inserted.
