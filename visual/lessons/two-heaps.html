Two Heaps

Split the numbers into a small half and a big half, each in its own heap; the median is always sitting on top of one or both of them.

Time to learn: about 1–2 hours · Prerequisites: Heaps, Top K

When to use it — the signal

"Median of a data stream", "running median", "middle value as numbers arrive", "sliding window median", "balance two groups so one side is always ≤ the other".

The idea in plain words

Numbers arrive one at a time: 5, 15, 1, 3, 8, 7. After each one, you must say the median (the middle value of the sorted list; with an even count, the average of the two middle values).

Re-sorting after every number costs O(n log n) each time. Instead, keep the numbers in two groups:

  • low: the smaller half, in a max-heap — its top is the biggest of the small numbers.
  • high: the bigger half, in a min-heap — its top is the smallest of the big numbers.

Keep two promises: every number in low ≤ every number in high, and the sizes differ by at most one (low may hold one extra). Then the middle of the sorted list is right at the tops: odd count → low.peek(); even count → the average of both tops.

Adding a number is a couple of heap operations, O(log n). Reading the median is O(1).

Analogy

A class lines up by height and splits into two rooms of equal size: short kids in one room, tall kids in the other. The tallest short kid and the shortest tall kid stand at the doors. The "middle height" is always one of the two kids at the doors — you never need to look inside the rooms.

Watch it work

Stream 5, 15, 1, 3, 8, 7. Each heap is drawn in sorted order so low then high reads like the sorted list; the highlighted box is each heap's top.

Same idea, written as "place, then rebalance"

Many people find this version easier to explain: compare with low's top to choose a side, then fix the sizes. Stream 2, 9, 4, 6, 1.

Why it works

"low holds the smaller half and high the bigger half, with sizes equal or low one bigger. So in sorted order the median is exactly low's maximum, or the average of low's maximum and high's minimum — the two heap tops. Each add is O(log n), each median read O(1)."

The template to remember

PriorityQueue<Integer> low  = new PriorityQueue<>(Collections.reverseOrder());
PriorityQueue<Integer> high = new PriorityQueue<>();
void add(int x) {
    low.offer(x);
    high.offer(low.poll());                         // keep order between halves
    if (high.size() > low.size()) low.offer(high.poll()); // keep sizes
}
double median() {
    return low.size() > high.size() ? low.peek() : (low.peek() + high.peek()) / 2.0;
}
Remember

Small half in a max-heap, big half in a min-heap; the median lives at the doors. Add to low, push low's top to high, give one back if high got bigger.

Common mistakes
  • Using two min-heaps — low must be a max-heap so its top is the biggest of the small half.
  • Integer division: (7 + 8) / 2 is 7, not 7.5. Divide by 2.0.
  • (a, b) -> b - a overflows for values near ±2³¹; use Collections.reverseOrder().
  • Only balancing sizes and forgetting the order promise — a big number can end up in low.
  • Sliding window median needs removal of old numbers: use lazy deletion with a counter map, or two TreeMaps.

Practice in this order

  • Hard295. Find Median from Data Stream — exactly the animations.
    Show solution

    The idea

    We get numbers one at a time and must answer "what is the middle value right now?" at any moment. For 1, 2, 3 the median is 2; for 1, 2 it is 1.5. The trick (two heaps): keep the smaller half in a max-heap (a heap whose top is its biggest value) and the larger half in a min-heap (top is its smallest). The median is then sitting right at the two tops.

    Brute force first

    Keep every number in a list, sort it on every findMedian call and read the middle. That costs O(n log n) per question, far too slow for many calls.

    Step by step

    1. low is a max-heap for the smaller half, high is a min-heap for the larger half.
    2. To add a number, push it into low, then move low's biggest into high. This keeps every value in low ≤ every value in high.
    3. If high now has more items than low, move high's smallest back to low. So low always has the same count or one more.
    4. Median: if low is bigger, it is low's top; otherwise it is the average of both tops.

    Java

    class MedianFinder {
    // low: a max-heap holding the smaller half
    private PriorityQueue<Integer> low =
        new PriorityQueue<>(Collections.reverseOrder());
    // high: a min-heap holding the larger half
    private PriorityQueue<Integer> high =
        new PriorityQueue<>();

    public MedianFinder() {}

    public void addNum(int num) {
        low.offer(num);            // always enter low first
        high.offer(low.poll());    // low's biggest moves up
        if (high.size() > low.size()) {
            low.offer(high.poll()); // keep low the same or +1
        }
    }

    public double findMedian() {
        if (low.size() > high.size()) return low.peek();
        return (low.peek() + (long) high.peek()) / 2.0;
    }
}

    Time O(log n) per add, O(1) per median · Space O(n) — each add does a few heap pushes and pops; we store every number once.

    Dry run

    add 1 → low [1], high []. add 2 → low [2,1], move 2 up → low [1], high [2]; sizes equal, median (1+2)/2 = 1.5. add 3 → low [3,1], move 3 up → high [2,3], high is bigger so move 2 back → low [2,1], high [3]; median = low top = 2.

    Watch out

    Adding two big ints like 2,147,483,647 + 2,147,483,647 overflows. Cast one to long (or divide as doubles) before adding. Also divide by 2.0, not 2, or you lose the .5.

  • Medium215. Kth Largest Element in an Array — warm up with one heap first.
    Show solution

    The idea

    Find the value that would be in position k if the array were sorted from biggest down. In [3,2,1,5,6,4] with k = 2 the answer is 5. Key insight (top-k with a heap): keep a min-heap of only the k largest numbers seen; its top is the smallest of those k, which is exactly the k-th largest.

    Brute force first

    Sort the array and return nums[n - k]. O(n log n) — fine, but interviewers want the heap (or quickselect).

    Step by step

    1. Make an empty min-heap.
    2. For every number, push it in.
    3. If the heap now holds more than k numbers, pop the smallest; it cannot be in the top k.
    4. At the end the heap holds the k largest, and its top is the answer.

    Java

    class Solution {
    public int findKthLargest(int[] nums, int k) {
        // min-heap that keeps only the k largest seen
        PriorityQueue<Integer> heap = new PriorityQueue<>();
        for (int x : nums) {
            heap.offer(x);
            if (heap.size() > k) heap.poll(); // drop smallest
        }
        return heap.peek(); // smallest of the k largest
    }
}

    Time O(n log k) · Space O(k) — each of n numbers does one push/pop on a heap of size k. (Quickselect, a partition step like quicksort that only recurses into one side, averages O(n) but has an O(n²) worst case.)

    Dry run

    [3,2,1,5,6,4], k = 2: push 3 → [3]; push 2 → [2,3]; push 1 → [1,2,3] too big, pop 1; push 5 → pop 2 → [3,5]; push 6 → pop 3 → [5,6]; push 4 → pop 4 → [5,6]. Top = 5.

    Watch out

    Java's PriorityQueue is a min-heap by default, which is what we want here. Using a max-heap of all n numbers also works but costs O(n) space.

  • Hard480. Sliding Window Median — two heaps plus lazy deletion.
    Show solution

    The idea

    Slide a window of size k across the array and report the median of each window. For [1,3,-1,-3,5,3,6,7], k = 3 the first window [1,3,-1] has median 1. It is problem 295 plus one twist: numbers also leave the window, and a normal heap cannot remove an item from the middle quickly. A TreeSet (a sorted set with O(log n) add, remove, first and last) can, so we use two TreeSets as our "two heaps".

    Brute force first

    For each window, copy it, sort it and take the middle. O(n · k log k).

    Step by step

    1. Store indices, not values, so equal values stay distinct; order them by value, then by index.
    2. low holds the smaller half, high the larger half, with low having the same size or one more.
    3. At index i, first remove index i − k (it just left the window) from whichever set has it.
    4. Add i to low, move low's largest to high, and if high got bigger move its smallest back (same dance as 295).
    5. Once the window is full, the median is low's last, or the average of low's last and high's first when sizes are equal.

    Java

    class Solution {
    public double[] medianSlidingWindow(int[] nums, int k) {
        // order indices by value, then by index (no ties)
        Comparator<Integer> cmp = (a, b) ->
            nums[a] != nums[b]
                ? Integer.compare(nums[a], nums[b])
                : Integer.compare(a, b);
        TreeSet<Integer> low = new TreeSet<>(cmp);  // small
        TreeSet<Integer> high = new TreeSet<>(cmp); // big
        double[] ans = new double[nums.length - k + 1];
        for (int i = 0; i < nums.length; i++) {
            if (i >= k) { // i-k left the window
                if (!low.remove(i - k)) high.remove(i - k);
            }
            low.add(i);
            high.add(low.pollLast()); // low's max moves up
            if (high.size() > low.size()) {
                low.add(high.pollFirst()); // rebalance
            }
            if (i >= k - 1) {            // window is full
                double mid = nums[low.last()];
                if (low.size() == high.size()) {
                    mid = (mid + nums[high.first()]) / 2.0;
                }
                ans[i - k + 1] = mid;
            }
        }
        return ans;
    }
}

    Time O(n log k) · Space O(k) — every step is a few TreeSet operations on at most k items. (The classic two-PriorityQueue version uses "lazy deletion": remember items to delete in a map and only throw them away when they reach a heap's top.)

    Dry run

    [1,3,-1], k = 3: low gets {-1,1}, high {3} → median = low's last = 1. Next window drops 1 and adds -3: low {-3,-1}, high {3} → median -1.

    Watch out

    Comparing with nums[a] - nums[b] overflows for values near ±2³¹; use Integer.compare. Average two values as doubles for the same reason. Without the index tie-break, a TreeSet would treat two equal values as one item and drop it.

  • Hard502. IPO — a min-heap by capital feeds a max-heap by profit.
    Show solution

    The idea

    You start with money w and may do at most k projects; each needs capital[i] in hand and adds profits[i] (you keep the capital). Greedy insight: at every step, among the projects you can afford right now, do the one with the biggest profit. Two heaps make this fast: a min-heap by capital holds locked projects, a max-heap by profit holds the affordable ones.

    Brute force first

    For each of the k rounds, scan every project to find the best affordable one. O(k · n).

    Step by step

    1. Put every project into the min-heap locked, ordered by capital needed.
    2. Each round, pop from locked every project whose capital is ≤ w and push its profit into the max-heap ready.
    3. If ready is empty, nothing is affordable: stop early.
    4. Otherwise pop the biggest profit and add it to w. Repeat up to k times.

    Java

    class Solution {
    public int findMaximizedCapital(int k, int w,
            int[] profits, int[] capital) {
        int n = profits.length;
        // min-heap by capital: cheapest project on top
        PriorityQueue<int[]> locked = new PriorityQueue<>(
            (a, b) -> Integer.compare(a[0], b[0]));
        for (int i = 0; i < n; i++) {
            locked.offer(new int[]{capital[i], profits[i]});
        }
        // max-heap of profits we can afford right now
        PriorityQueue<Integer> ready =
            new PriorityQueue<>(Collections.reverseOrder());
        while (k-- > 0) {
            // unlock every project our money now covers
            while (!locked.isEmpty()
                    && locked.peek()[0] <= w) {
                ready.offer(locked.poll()[1]);
            }
            if (ready.isEmpty()) break; // nothing affordable
            w += ready.poll();          // take the best one
        }
        return w;
    }
}

    Time O((n + k) log n) · Space O(n) — each project enters and leaves each heap at most once.

    Dry run

    k = 2, w = 0, profits [1,2,3], capital [0,1,1]. Round 1: unlock project 0 → ready {1}, take 1, w = 1. Round 2: unlock projects 1 and 2 → ready {2,3}, take 3, w = 4. Answer 4.

    Watch out

    Do not forget the early stop when nothing is affordable; looping on an empty heap throws. Money only grows, so a project unlocked once stays unlocked; never put it back into locked.

  • Medium436. Find Right Interval — two heaps sorted by start and by end.
    Show solution

    The idea

    For each interval, find the interval whose start is the smallest value that is still ≥ this interval's end, and return its index (or −1). For [[3,4],[2,3],[1,2]] the answer is [-1,0,1]: [2,3] ends at 3 and [3,4] starts at 3. Insight: this is a "smallest key ≥ x" lookup, which a sorted map answers in O(log n).

    Brute force first

    For every interval, scan all others for the smallest valid start. O(n²).

    Step by step

    1. Put every start into a TreeMap (a sorted map), mapping start → its index. Starts are unique.
    2. For each interval, ask ceilingEntry(end): the entry with the smallest key ≥ end.
    3. If there is one, store its index; otherwise store −1.

    Java

    class Solution {
    public int[] findRightInterval(int[][] intervals) {
        // start value -> index (all starts are unique)
        TreeMap<Integer, Integer> starts = new TreeMap<>();
        for (int i = 0; i < intervals.length; i++) {
            starts.put(intervals[i][0], i);
        }
        int[] ans = new int[intervals.length];
        for (int i = 0; i < intervals.length; i++) {
            // smallest start that is >= my end
            Map.Entry<Integer, Integer> e =
                starts.ceilingEntry(intervals[i][1]);
            ans[i] = e == null ? -1 : e.getValue();
        }
        return ans;
    }
}

    Time O(n log n) · Space O(n) — n inserts and n lookups in a sorted map. (The two-heap way: pop intervals by largest end, and pop a max-heap of starts while its top start ≥ that end, keeping the last one popped as the answer.)

    Dry run

    [[3,4],[2,3],[1,2]]: map {1→2, 2→1, 3→0}. End 4: no key ≥ 4 → -1. End 3: key 3 → index 0. End 2: key 2 → index 1. Result [-1,0,1].

    Watch out

    An interval can be its own right interval when start == end (like [1,1]); ceilingEntry handles that because "≥" includes equal. Use ≥, not >.

Test yourself

After 1, 2, 3, 4 have arrived, what is in low and high, and what is the median?

low = {1, 2} (top 2), high = {3, 4} (top 3). Median = (2 + 3) / 2 = 2.5.

Why is low a max-heap and high a min-heap, not the other way round?

The median is next to the boundary between the halves: the biggest small number and the smallest big number. Those are exactly the tops of a max-heap of the small half and a min-heap of the big half.

What is the cost of addNum and findMedian?

addNum O(log n) — at most three heap operations. findMedian O(1) — two peeks.
