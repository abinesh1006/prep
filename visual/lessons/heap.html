Heaps

A heap always knows its smallest (or largest) item, lets you remove it, and accepts new items — each in O(log n) — using a tree that secretly lives in a plain array.

Time to learn: about 2 hours · Prerequisites: Big-O, Stacks and queues

When to use it — the signal

"Repeatedly take the smallest / largest", "k largest", "k closest", "merge k sorted", "schedule the next task", "median of a stream", "cheapest next step" (Dijkstra). If you would sort again and again after every insert, you want a heap.

The idea in plain words

A min-heap is a binary tree with one rule: every parent is ≤ its children. So the smallest value is always at the root. It does not keep everything sorted — only "parent beats children" — and that weaker rule is why it is fast.

The tree is always complete (filled level by level, left to right), so it fits in an array with no gaps:

  • children of index i are at 2i + 1 and 2i + 2
  • parent of index i is at (i − 1) / 2
  • example: index 1's children are 3 and 4; index 4's parent is (4 − 1) / 2 = 1

Insert (sift-up): put the new value at the end of the array, then while it is smaller than its parent, swap them. It climbs at most the height of the tree, about log₂ n levels — 20 swaps for a million items.

Poll / remove the min (sift-down): take the root, move the last value into the root, then while it is bigger than its smaller child, swap with that child. Again at most log₂ n steps.

In Java: PriorityQueue<Integer> is a min-heap. For a max-heap, pass Collections.reverseOrder().

Analogy

A company org chart where every boss is more senior than the people under them. A new hire joins at the bottom; if they are more senior than their boss, they swap places, and keep climbing until their boss outranks them. When the CEO leaves, the newest bottom person temporarily takes the seat and gets demoted step by step until everyone below is junior to them.

Why it works

"A heap only promises that every parent is smaller than its children, so the root is the minimum. Insert and poll each repair that promise along one root-to-leaf path, and a complete tree has height log n, so both are O(log n); peek is O(1)."

The template to remember

PriorityQueue<Integer> minH = new PriorityQueue<>();
PriorityQueue<Integer> maxH = new PriorityQueue<>(Collections.reverseOrder());
PriorityQueue<int[]> byDist = new PriorityQueue<>((a, b) -> a[0] - b[0]);
minH.offer(x);      // O(log n)  sift-up
minH.peek();        // O(1)      the smallest
minH.poll();        // O(log n)  sift-down
// array view: kids 2i+1, 2i+2   parent (i-1)/2
Remember

Insert at the end and bubble up; remove the root, put the last in its place, sink down. Kids 2i+1, 2i+2 — parent (i−1)/2.

Common mistakes
  • Thinking a heap is sorted. Only the root is guaranteed; iterating a PriorityQueue does not give sorted order.
  • Sift-down swapping with the left child instead of the smaller child — the rule breaks one level up.
  • Comparator (a, b) -> a - b can overflow for huge values; use Integer.compare(a, b).
  • pq.remove(x) of an arbitrary element is O(n), not O(log n).
  • Building a heap from n items with n offers is O(n log n); new PriorityQueue<>(list) heapifies in O(n).

Test yourself

In a heap array, where are the children of index 2, and where is the parent of index 6?

Children at 5 and 6. Parent of 6 is (6 − 1) / 2 = 2.

Is [1, 4, 2, 7, 3] a valid min-heap?

No. Index 1 (value 4) has a child at index 4 with value 3, and 3 < 4.

Why does poll move the last element to the root instead of promoting a child?

Removing the last slot keeps the tree complete (no gaps in the array). Then a single sift-down fixes the order.

You need the largest values but Java's PriorityQueue is a min-heap. What do you do?

new PriorityQueue<>(Collections.reverseOrder()), or a comparator (a, b) -> Integer.compare(b, a).
