Recursion

A function that solves a big problem by calling itself on a smaller copy of the same problem, until the problem is so small the answer is obvious.

Time to learn: about 3 hours (take your time — every tree, graph, backtracking and DP lesson builds on this one) · Prerequisites: Big-O, Stack basics

When to use it — the signal

The problem is made of smaller copies of itself: a tree ("for every node..."), a folder inside a folder, a nested list, "all the ways to...", "split in half and solve each half", or a formula that uses its own earlier values like n! = n × (n−1)! or fib(n) = fib(n−1) + fib(n−2).

The idea in plain words

Recursion = a function that calls itself. That sounds like it would go on forever, so every recursive function has two parts:

  • Base case — the smallest version of the problem, answered directly with no more calls. Example: 1! = 1. This is the "stop" sign.
  • Recursive step — make the problem a bit smaller, call yourself on the smaller one, and use its answer. Example: 4! = 4 × 3!.

Here is the key trick, called "trust the recursion". When you write fact(4), do not try to follow fact(3), fact(2), fact(1) in your head. Just assume fact(3) correctly returns 6. Then your only job is one small step: 4 × 6 = 24. If the base case is right and each step is right, the whole thing is right (this is the same logic as falling dominoes).

A real-life version: you sit in a dark cinema and want to know your row number. You ask the person in front: "what row are you in?" They do not know either, so they ask the person in front of them, and so on. The person in row 1 can see the screen and says "1" (base case). Each person adds 1 to the answer they hear and passes it back. Nobody had to count the whole cinema.

How does the computer remember who is waiting? It keeps a call stack — a pile of paused calls (a stack = last in, first out, like a pile of plates). Each call is one frame on the pile, holding its own copy of the variables. A new call goes on top; when it returns, it is removed and the call under it continues from where it paused.

Cost: time = number of calls × work per call. Extra space = the deepest the pile ever gets (the recursion depth), because every waiting frame uses memory.

Analogy

Russian dolls. To find the tiny solid doll, you open the big doll and find a smaller doll inside — the same problem, just smaller. You keep opening until you reach the tiny doll that does not open (the base case). Then you close them back up in reverse order: the last doll opened is the first one closed. That "reverse order on the way back" is exactly the call stack. Two mirrors facing each other show the same picture getting smaller and smaller — but a mirror has no base case, which is why it goes on forever. Your code must not.

Watch it work

1. Factorial: going down, then coming back up

Compute fact(4) = 4 × 3 × 2 × 1. Colours: yellow = the call running right now, blue = paused, waiting for an answer from below, green = finished (the small label under it is what it returned), faded = not called yet.

2. Fibonacci: one call can make two calls (a tree of calls)

fib(n) = fib(n−1) + fib(n−2), with fib(0) = 0 and fib(1) = 1. Now each call makes two calls, so the calls form a tree. The left child is the fib(n−1) call, the right child is the fib(n−2) call. The stack only ever holds one path from the top call down to the running call.

3. "Trust the recursion": sum of an array

Sum [3, 1, 4, 2] by recursion. Read the function as a sentence: "the sum from index i to the end = nums[i] + the sum from i+1 to the end". The shaded box is the "smaller doll" each call hands to the next one. While writing the code, you only think about one call and trust the shaded part.

Why it works

"If the base case returns the right answer, and each call returns the right answer assuming the smaller call does, then by induction (falling dominoes) every call is right. Every call must move closer to the base case, or it never stops. Time is calls × work per call; space is the maximum depth of the call stack."

The template to remember

Result solve(Problem p) {
    if (p is tiny) return directAnswer;   // 1. base case first
    Result sub = solve(smaller(p));         // 2. trust the smaller call
    return combine(p, sub);                 // 3. one small step of my own
}

Before writing any recursive function, say these three lines out loud: "What is the smallest input and its answer? How do I make the input smaller? Given the smaller answer, how do I build mine?"

The hidden data structure of recursion is the call stack; its depth is the space cost, and adding a memo array is the first step towards dynamic programming.

Remember

Base case first. Shrink the problem. Trust the call. The stack goes down to the base case, then answers come back up in reverse order.

Common mistakes
  • No base case, or a base case that can be skipped (e.g. if (n == 0) but you call with n − 2 from 1 → −1, −3, ...). Result: StackOverflowError.
  • The recursive call does not make the problem smaller (calling f(n) inside f(n)).
  • Calling the function but ignoring its return value — writing fact(n - 1); instead of return n * fact(n - 1);.
  • Tracing every call in your head while writing. Trace small inputs only when debugging; while writing, trust the call.
  • Forgetting the stack space: depth 100,000 (a long list or a skewed tree) overflows Java's default stack. Say "O(depth) extra space".
  • Exponential repeats like naive fib: the same sub-call is made many times. Fix with memoization (store answers) — see DP intro.

Practice in this order

  • Easy509. Fibonacci Number — exactly animation 2; then add a memo array.
    Show solution

    The idea

    F(0) = 0, F(1) = 1, and F(n) = F(n-1) + F(n-2). F(4) = 3. The plain recursion recomputes the same values again and again (the call tree doubles). The insight: memoization (save each answer the first time) so every F(i) is computed once. Pattern: recursion + memo.

    Brute force first

    Plain return fib(n-1) + fib(n-2): correct but O(2n) calls, because fib(2) is solved many times.

    Step by step

    1. Base cases: n <= 1 returns n.
    2. Make a memo array of size n + 1 (0 means "not computed yet"; real values for n ≥ 2 are ≥ 1).
    3. Before computing f(n), check the memo; if filled, return it.
    4. Otherwise compute f(n-1) + f(n-2), store it, return it.

    Java

    class Solution {
    private int[] memo;

    public int fib(int n) {
        memo = new int[n + 1];
        return f(n);
    }

    private int f(int n) {
        if (n <= 1) return n;            // base cases
        if (memo[n] != 0) return memo[n]; // already known
        memo[n] = f(n - 1) + f(n - 2);
        return memo[n];
    }
}

    Time O(n) · Space O(n) — each value is computed once; the memo and the call stack are n deep.

    Dry run

    fib(4) → f(3) → f(2) → f(1)=1 + f(0)=0 = 1 (saved); f(3) = 1 + f(1) = 2 (saved); f(4) = 2 + f(2) from memo = 3.

    Watch out

    new int[n + 1] works even for n = 0 (size 1). An iterative two-variable loop gives O(1) space, mention it as the follow-up.

  • Easy231. Power of Two — base case n == 1, step n / 2.
    Show solution

    The idea

    Is n equal to 1, 2, 4, 8, ...? 16 → true, 3 → false. Recursive thinking: n is a power of two if it is 1, or if it is even and n / 2 is a power of two. Base case n == 1, step n / 2.

    Step by step

    1. If n <= 0: false (no power of two is zero or negative).
    2. If n == 1: true (20).
    3. If n is odd: false.
    4. Otherwise answer for n / 2.

    Java

    class Solution {
    public boolean isPowerOfTwo(int n) {
        if (n <= 0) return false;
        if (n == 1) return true;      // base case 2^0
        if (n % 2 != 0) return false; // odd and > 1
        return isPowerOfTwo(n / 2);   // smaller problem
    }
}

    Time O(log n) · Space O(log n) — n halves each call, and each call waits on the stack.

    Dry run

    16 → 8 → 4 → 2 → 1 true. 12 → 6 → 3 odd → false.

    Watch out

    Handle n <= 0 first (Integer.MIN_VALUE is even but negative). The O(1) bit trick is n > 0 && (n & (n - 1)) == 0.

  • Easy206. Reverse Linked List — trust reverse(head.next), then fix one pointer.
    Show solution

    The idea

    Reverse a singly linked list: 1→2→3 becomes 3→2→1. Recursive insight: trust that reverse(head.next) reverses the rest and returns its new head. After that, head.next is the tail of the reversed part, so hang head after it and cut head's old link.

    Step by step

    1. Base case: empty list or one node is already reversed; return head.
    2. newHead = reverseList(head.next).
    3. The node after head is now the last node of the reversed part: head.next.next = head.
    4. head.next = null so head becomes the new tail.
    5. Return newHead.

    Java

    class Solution {
    public ListNode reverseList(ListNode head) {
        if (head == null || head.next == null) return head;
        ListNode newHead = reverseList(head.next); // trust it
        head.next.next = head; // old next now points back
        head.next = null;      // head is the new tail
        return newHead;
    }
}

    Time O(n) · Space O(n) — one call per node, and the calls stack up n deep.

    Dry run

    1→2→3: reverse(3) returns 3. Back in node 2: 3.next = 2, 2.next = null → 3→2. Back in node 1: 2.next = 1, 1.next = null → 3→2→1.

    Watch out

    Forgetting head.next = null leaves a cycle between the first two nodes. The iterative version (prev/curr pointers) uses O(1) space; interviewers often ask for both.

  • Easy21. Merge Two Sorted Lists — pick the smaller head, trust the merge of the rest.
    Show solution

    The idea

    Join two sorted linked lists into one sorted list. 1→2→4 + 1→3→4 → 1→1→2→3→4→4. Recursive insight: the smaller head must come first; then trust that merging the rest gives a sorted list, and attach it after that head.

    Step by step

    1. If one list is empty, return the other.
    2. If a.val <= b.val: a.next = merge(a.next, b), return a.
    3. Otherwise: b.next = merge(a, b.next), return b.

    Java

    class Solution {
    public ListNode mergeTwoLists(ListNode a, ListNode b) {
        if (a == null) return b;
        if (b == null) return a;
        if (a.val <= b.val) {
            a.next = mergeTwoLists(a.next, b); // rest
            return a;
        }
        b.next = mergeTwoLists(a, b.next);
        return b;
    }
}

    Time O(n + m) · Space O(n + m) — one call per node placed, all on the call stack.

    Dry run

    [1,2,4] vs [1,3,4]: pick a's 1, then b's 1, then 2, 3, a's 4, then a is empty → attach b's 4. Result 1,1,2,3,4,4.

    Watch out

    Both base cases are needed (either list can run out first). For very long lists the recursion depth can overflow the stack; an iterative version with a dummy head node avoids that.

  • Medium50. Pow(x, n) — x^n = (x^(n/2))², depth log n.
    Show solution

    The idea

    Compute xn, where n can be negative or as large as 231. Multiplying n times is too slow. The insight (fast power): x^n = (x^(n/2))², times one extra x when n is odd. Each call halves n, so the depth is only about log n.

    Brute force first

    Multiply x by itself |n| times: O(n), about 2×109 steps for the largest n: too slow.

    Step by step

    1. Convert n to a long N (so −231 can be negated safely).
    2. If N is negative: use 1/x and −N.
    3. Recursive helper: if N == 0 return 1.
    4. half = pow(x, N / 2); return half * half, times x if N is odd.

    Java

    class Solution {
    public double myPow(double x, int n) {
        long N = n;           // -2^31 can't be negated as int
        if (N < 0) {
            x = 1 / x;
            N = -N;
        }
        return pow(x, N);
    }

    private double pow(double x, long n) {
        if (n == 0) return 1;
        double half = pow(x, n / 2); // solve half once
        return n % 2 == 0 ? half * half : half * half * x;
    }
}

    Time O(log n) · Space O(log n) — n halves each call; the calls stack log n deep.

    Dry run

    pow(2,10) = pow(2,5)^2
pow(2,5)  = pow(2,2)^2 * 2
pow(2,2)  = pow(2,1)^2
pow(2,1)  = pow(2,0)^2 * 2 = 2
back up: 4 -> 4*4*2 = 32 -> 32*32 = 1024

    Watch out

    -n overflows for n = Integer.MIN_VALUE; that is why we use long. Call pow(x, n / 2) once and reuse it; calling it twice brings back O(n).

  • Medium779. K-th Symbol in Grammar — answer for row n comes from row n−1.
    Show solution

    The idea

    Row 1 is 0. Each next row replaces 0 with 01 and 1 with 10: 0, 01, 0110, ... Return the k-th symbol (1-based) of row n. The insight: symbol k of row n is made by its parent, symbol (k + 1) / 2 of row n − 1. An odd k copies the parent; an even k is its opposite.

    Brute force first

    Build every row as a string: row n has 2n−1 symbols, about 5×108 for n = 30. Far too big.

    Step by step

    1. Base case: n == 1 returns 0.
    2. Find the parent: p = kthGrammar(n - 1, (k + 1) / 2).
    3. If k is odd, it is the left child: same as p.
    4. If k is even, it is the right child: 1 - p.

    Java

    class Solution {
    public int kthGrammar(int n, int k) {
        if (n == 1) return 0;
        int parent = kthGrammar(n - 1, (k + 1) / 2);
        // odd k: left child = parent; even k: flipped
        return k % 2 == 1 ? parent : 1 - parent;
    }
}

    Time O(n) · Space O(n) — one call per row, n calls deep.

    Dry run

    Row 3 is 0110, k = 3. Parent: row 2, k = 2 → parent row 1, k = 1 = 0; k = 2 even → 1. Back in row 3: k = 3 odd → same as parent → 1. Check: 0110[3] = 1.

    Watch out

    k is 1-based: the parent is (k + 1) / 2, not k / 2. Never build the strings. A neat O(1)-ish shortcut: the answer is the parity of Integer.bitCount(k - 1).

Test yourself

What two parts must every recursive function have?

A base case (answered directly, no more calls) and a recursive step that calls itself on a strictly smaller input and uses that answer.

fact(5) is called. How many frames are on the stack at the deepest moment?

5: fact(5), fact(4), fact(3), fact(2), fact(1). So the extra space is O(n).

Why is naive fib(n) slow, even though each call does O(1) work?

Each call makes two calls, so the call tree has about 2ⁿ nodes, and the same values (like fib(2)) are recomputed again and again. Storing each answer once (memoization) makes it O(n).

What does "trust the recursion" mean when you write the code?

Assume the call on the smaller input already returns the correct answer, and only write the one step that turns that answer into yours. Do not trace the whole call tree while writing.

What happens with int f(int n) { return n + f(n - 1); }?

There is no base case, so it calls itself forever (n goes 3, 2, 1, 0, −1, ...) until the stack runs out: StackOverflowError. Add if (n == 0) return 0;.
