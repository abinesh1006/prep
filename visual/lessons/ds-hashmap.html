HashMap & HashSet

A HashMap turns a key into an array index with a little arithmetic, so it can find a value in about one step instead of searching. It is an array of buckets; each bucket holds the few entries whose keys landed there.

Time to learn: about 2.5 hours · Prerequisites: Array & ArrayList, Linked list

Use it when you need…
  • "Have I seen this before?" — set.contains(x) in O(1) average.
  • "Where / how many times did I see it?" — map.get(x), map.merge(x, 1, Integer::sum) in O(1) average.
  • To group things by a key (anagrams by sorted letters, nodes by level).
  • To remember results you already computed (memoization).

In plain words

Keys can be anything — strings, numbers, lists — but arrays only understand integer positions. A HashMap bridges the gap in two steps. First, every Java object can produce an int called its hash code (key.hashCode()). Second, the map squeezes that int into the range of its array: with 16 buckets, keep only the last 4 bits, giving an index from 0 to 15. The entry is stored in that bucket.

Different keys sometimes land in the same bucket — a collision. That is normal. Java keeps every entry of a bucket in a small linked chain and, to find a key, walks that chain comparing with equals. As long as the chains stay short, every operation is about one step. To keep them short, the map doubles its array whenever it is 75% full and redistributes the entries.

Analogy

A cloakroom with numbered hooks. The attendant does not search all the coats: she looks at your ticket, does a quick calculation, and walks straight to hook 7. If two coats ended up on hook 7, she checks the two name tags and hands over the right one. When the hooks get crowded, the club installs twice as many hooks and re-hangs every coat on its new number.

Build it yourself

Separate chaining with a power-of-two table, the same hash spreading and the same lo/hi split on resize as the JDK. Tested against java.util.HashMap with 50,000 random put/get/remove operations, including a null key.

import java.util.Objects;

// Hash map with separate chaining, like java.util.HashMap.
public class MyHashMap<K, V> {
    private static class Node<K, V> {
        final int hash;   // cached, never recomputed
        final K key;
        V val;
        Node<K, V> next;  // next node in the same bucket
        Node(int hash, K key, V val) {
            this.hash = hash; this.key = key; this.val = val;
        }
    }

    private Node<K, V>[] table = newTable(16); // power of 2
    private int size = 0;

    // Mix the high bits into the low bits.
    static int hash(Object key) {
        int h = key == null ? 0 : key.hashCode();
        return h ^ (h >>> 16);
    }

    public V get(Object key) {
        int h = hash(key);
        int i = h & (table.length - 1);   // = h % length
        for (Node<K, V> e = table[i]; e != null; e = e.next)
            if (e.hash == h && Objects.equals(e.key, key))
                return e.val;
        return null;                      // not found
    }

    public V put(K key, V val) {
        int h = hash(key);
        int i = h & (table.length - 1);
        Node<K, V> e = table[i], last = null;
        while (e != null) {               // walk the chain
            if (e.hash == h && Objects.equals(e.key, key)) {
                V old = e.val;            // same key:
                e.val = val;              // replace value
                return old;
            }
            last = e;
            e = e.next;
        }
        Node<K, V> n = new Node<>(h, key, val);
        if (last == null) table[i] = n;   // empty bucket
        else last.next = n;               // append to chain
        if (++size > table.length * 3 / 4) resize();
        return null;
    }

    public V remove(Object key) {
        int h = hash(key);
        int i = h & (table.length - 1);
        Node<K, V> e = table[i], prev = null;
        while (e != null) {
            if (e.hash == h && Objects.equals(e.key, key)) {
                if (prev == null) table[i] = e.next;
                else prev.next = e.next;  // skip over e
                size--;
                return e.val;
            }
            prev = e;
            e = e.next;
        }
        return null;
    }

    public int size() { return size; }

    // Double the table. Each node stays at i or moves to i+n.
    private void resize() {
        Node<K, V>[] old = table;
        int n = old.length;
        table = newTable(n * 2);
        for (int i = 0; i < n; i++) {
            Node<K, V> loH = null, loT = null;
            Node<K, V> hiH = null, hiT = null;
            for (Node<K, V> e = old[i]; e != null; e = e.next) {
                if ((e.hash & n) == 0) {      // new bit 0: stay
                    if (loT == null) loH = e; else loT.next = e;
                    loT = e;
                } else {                      // new bit 1: move
                    if (hiT == null) hiH = e; else hiT.next = e;
                    hiT = e;
                }
            }
            if (loT != null) { loT.next = null; table[i] = loH; }
            if (hiT != null) { hiT.next = null; table[i + n] = hiH; }
        }
    }

    @SuppressWarnings("unchecked")
    private static <K, V> Node<K, V>[] newTable(int cap) {
        return (Node<K, V>[]) new Node[cap];
    }
}

In the resize loop, loT.next = e changes the previous node's next, never e.next, so the walk over the old chain is not disturbed. The final loT.next = null cuts off whatever followed in the old chain.

The real Java class

  • Fields: Node<K,V>[] table, int size, int threshold (= capacity × load factor), float loadFactor, modCount. Node is { final int hash; final K key; V value; Node next; }.
  • Lazy table: new HashMap<>() allocates nothing; the first put creates 16 buckets. Default load factor 0.75 → first resize when the 13th entry arrives.
  • Power-of-two capacity: new HashMap<>(100) rounds up to 128 (tableSizeFor), so index = hash & (n − 1) works. That only uses the low bits, hence the spreading hash ^ (hash >>> 16).
  • Resize doubles the table and splits each bucket into a "lo" list (stays at i) and a "hi" list (moves to i + oldCap), keeping the order — decided by one bit, (hash & oldCap) == 0.
  • Java 7 vs 8: Java 7 inserted at the head of a chain; a resize racing with another thread could link a chain into a cycle and hang get forever. Java 8 appends at the tail and splits in order. HashMap is still not thread-safe — use ConcurrentHashMap.
  • Treeify (Java 8+): when one bucket's chain grows beyond 8 nodes (TREEIFY_THRESHOLD) and the table has at least 64 buckets (MIN_TREEIFY_CAPACITY), the chain becomes a red-black tree of TreeNodes; with a smaller table it just resizes instead. When a resize shrinks a tree bin to 6 or fewer (UNTREEIFY_THRESHOLD), it turns back into a chain. Tree nodes are ordered by hash, then by compareTo if the keys are Comparable. This caps a bucket's worst case at O(log n) — protection against bad hash codes or deliberate attacks.
  • null: one null key is allowed (hash 0, bucket 0) and any number of null values. ConcurrentHashMap and Hashtable allow neither.
  • Iteration order is unspecified and changes after a resize. LinkedHashMap = insertion order (or access order); TreeMap = sorted.
  • Sizing: new HashMap<>(n) means capacity n, not "n entries without resizing". Java 19+ has HashMap.newHashMap(n), which sizes for n entries.
  • Handy methods: getOrDefault, putIfAbsent, merge(k, 1, Integer::sum) for counting, computeIfAbsent(k, x -> new ArrayList<>()).add(v) for grouping.

hashCode and equals — the contract

  • If a.equals(b) then a.hashCode() == b.hashCode(). Must hold, or equal keys land in different buckets and get misses.
  • Equal hash codes do not require equal objects ("Aa" and "BB"). Collisions are legal, only slower.
  • Both must be stable while the object is a key: build them from fields that never change (see the mutable-key trap).
  • Override both or neither. Overriding only equals → two "equal" keys get identity hash codes from Object → duplicates in a HashSet.
  • Java 16+ records generate correct equals/hashCode from their fields — the easiest safe key: record Point(int r, int c) {}. Otherwise Objects.hash(a, b, c).
  • Arrays use identity: int[] as a key compares references, not contents. Use List<Integer>, a String like "3,5", a record, or Arrays.hashCode/Arrays.equals in a wrapper.

HashSet is a HashMap

HashSet<E> contains a HashMap<E, Object> and stores every element as a key with the same dummy value PRESENT. set.add(x) is map.put(x, PRESENT) == null — true if x was new. So everything on this page (buckets, resize, treeify, the hashCode/equals contract) applies to HashSet too. LinkedHashSet wraps a LinkedHashMap in the same way.

Why and when to use it

  • Membership tests and de-duplication: HashSet.
  • Counting: map.merge(x, 1, Integer::sum) — or a plain int[26] when keys are small letters (faster still).
  • "Complement seen before?" in one pass: Two Sum stores value → index.
  • Prefix-sum counts (map.get(sum - k)), grouping (anagrams), graph adjacency for arbitrary node labels, memoization keys.
  • Index for another structure: key → node in an LRU cache, key → heap entry.

When not to use it

  • You need keys in sorted order, or floor/ceiling/range queries → TreeMap/TreeSet (O(log n)).
  • Keys are small dense integers (0..n, letters) → an array: no hashing, no boxing, no nodes.
  • You need insertion order → LinkedHashMap; access order for eviction → LinkedHashMap(…, true).
  • Shared between threads → ConcurrentHashMap (never a plain HashMap).
  • Need the min or max repeatedly → PriorityQueue.

Used in these patterns

  • Arrays & hashing — Two Sum, group anagrams, contains duplicate.
  • Prefix sum — count of earlier prefix sums; Sliding window — character counts in the window.
  • LRU cache and Design problems — key → node.
  • Graph basics, Grid BFS/DFS, Topological sort, Advanced graphs — adjacency maps and visited sets.
  • DP intro, Advanced DP, Recursion — memo maps.
  • Top-k — count with a map, then a heap; Trie — children maps; Strings & palindromes.
  • Union-find — parent map when nodes are not 0..n−1.
Remember

hashCode → spread (h ^ h>>>16) → index (h & n−1) → walk the bucket with equals. Table is a power of two, doubles at 75% full, nodes stay at i or move to i + n. Chains over 8 in a table of 64+ become red-black trees. Equal objects must have equal hash codes; never mutate a key. HashSet = HashMap with dummy values.

Common mistakes
  • Overriding equals without hashCode (or the reverse) on a key class.
  • Using int[] or char[] as a key — compared by reference. Convert to String (new String(chars)) or a List.
  • Mutating a key (a List, a mutable object) after put.
  • map.get(k) + 1 when k is absent → unboxing null → NullPointerException. Use getOrDefault(k, 0) or merge.
  • Comparing Integer values from a map with == (fails above 127). Use .equals or unbox.
  • Relying on iteration order of a HashMap — it is not insertion order and changes with resizes.
  • Modifying the map while iterating over keySet() → ConcurrentModificationException. Use iterator.remove() or entrySet().removeIf(...).
  • Saying "HashMap is always O(1)" in an interview without the words average and good hash function.

Interview questions on the internals

Walk me through what happens in map.put(k, v).

Compute h = k.hashCode() ^ (h >>> 16); index i = h & (n − 1); if bucket i is empty, place a new Node. Otherwise walk the chain (or tree): if a node has the same hash and equals the key, replace its value and return the old one; else append a new node. Then ++size; if it exceeds capacity × 0.75, resize. If the chain passed 8 nodes, treeify (or resize if the table is under 64).

Why is the capacity always a power of two?

So the index is hash & (n − 1) — a single AND instead of a slower modulo, never negative — and so resize can split each bucket with one bit test: a node stays at i or moves to i + oldCap.

Why does HashMap do h ^ (h >>> 16)?

With a power-of-two table only the low bits pick the bucket. Hash codes that differ only in their high bits (common for floats, some IDs) would all collide. XOR-ing the top half into the bottom half lets every bit influence the index, cheaply.

What is the load factor, and what happens if you change it?

The fill ratio that triggers a resize (default 0.75). Lower → fewer collisions but more memory and more resizes; higher → less memory but longer chains. 0.75 is a good time/space balance.

What is treeification and when does it happen?

Since Java 8, a bucket whose chain exceeds 8 nodes is converted into a red-black tree — but only if the table has at least 64 buckets; otherwise the map resizes instead. Trees shrink back to chains at 6 or fewer nodes during a resize split. It makes the worst case O(log n) per bucket.

What breaks if two equal objects have different hash codes?

They usually go to different buckets, so get with an equal key looks in the wrong bucket and returns null, and a HashSet can hold both "duplicates".

Why should HashMap keys be immutable?

The bucket is chosen from the hash at insert time and the hash is cached in the node. If the key's fields change, its new hash points to a different bucket and its equals may no longer match — the entry becomes unreachable.

How is HashSet implemented?

As a HashMap whose keys are the set elements and whose values are one shared dummy object, PRESENT. add returns whether put returned null.

How do you build an LRU cache with LinkedHashMap?

Extend it with the constructor super(cap, 0.75f, true) for access order and override removeEldestEntry to return size() > cap. get moves an entry to the end; inserts past capacity evict the head.

HashMap vs Hashtable vs ConcurrentHashMap?

HashMap: not thread-safe, allows one null key and null values. Hashtable: legacy, every method synchronized on one lock, no nulls. ConcurrentHashMap: thread-safe with fine-grained locking/CAS per bucket, no nulls, the right choice for shared maps.
