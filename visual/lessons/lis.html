Longest Increasing Subsequence

For each number, ask "what is the longest rising run that ends here?" — then speed it up by keeping only the smallest possible ending for each length.

Time to learn: about 2.5 hours · Prerequisites: DP intro, Binary search

When to use it — the signal

"Longest increasing subsequence", "longest chain", "maximum number of envelopes you can nest", "longest sequence where each item is bigger than the one before". A subsequence = items kept in their original order, but you may skip items (they do not have to be next to each other).

The idea in plain words

Take [10, 9, 2, 5, 3, 7, 101, 18]. One increasing subsequence is 2, 5, 7, 101 — length 4, and nothing longer exists.

O(n²) version. Let dp[i] = length of the longest increasing subsequence that ends exactly at index i. Every number alone is a run of length 1. For index i, look at every earlier index j: if nums[j] < nums[i], the run ending at j can be extended by nums[i], giving dp[j] + 1. Keep the best. The answer is the largest dp value anywhere (the best run may end anywhere).

O(n log n) version. Keep an array tails: tails[k] = the smallest number that can end an increasing run of length k + 1. A small ending is better, because more future numbers can extend it. For each new number x:

  • If x is bigger than every tail, it extends the longest run → append it.
  • Otherwise find (by binary search) the first tail ≥ x and replace it with x — same length, smaller ending.

The length of tails is the answer. Careful: tails itself is not always a real subsequence; only its length is meaningful.

Analogy

Patience, the card game: deal cards one at a time onto piles; a card goes on the leftmost pile whose top card is bigger or equal, or starts a new pile on the right. The number of piles at the end is the length of the longest increasing subsequence. The pile tops are the tails array.

Why it works

"dp[i] fixes the last element of the subsequence, which is what makes the subproblem well defined: any run ending at i is a run ending at some smaller j plus nums[i]. In the fast version, tails stays sorted, and replacing a tail with a smaller value never shortens any run — it only makes future extensions easier — so binary search finds where each number belongs."

The template to remember

// O(n²)
for (i) for (j < i) if (a[j] < a[i]) dp[i] = max(dp[i], dp[j] + 1);
// O(n log n)
for (x : a) { pos = firstIndexWith(tails[pos] >= x);
              if (pos == size) tails.add(x); else tails.set(pos, x); }
Remember

dp[i] = longest run ending at i; answer = max of dp. Fast: tails, binary search, replace or append.

Common mistakes
  • Returning dp[n-1] instead of the maximum over all dp — the best run need not end at the last number.
  • Searching for the first tail > x instead of ≥ x: that allows equal numbers, which breaks "strictly increasing".
  • Thinking tails is the subsequence. To print one, store a parent index per element.
  • Russian Doll Envelopes: sort width ascending but height descending for equal widths, then LIS on heights.

Test yourself

For [3, 1, 2], what is dp and what is the answer?

dp = [1, 1, 2]; the answer is 2 (1, 2).

Why replace a tail with a smaller number instead of ignoring the number?

A run of the same length that ends lower can be extended by more future numbers. Ignoring it could miss a longer run later.

Is tails always sorted? Why does that matter?

Yes, strictly increasing — a longer run's end is always bigger than a shorter run's best end. That is what lets us binary search it.
